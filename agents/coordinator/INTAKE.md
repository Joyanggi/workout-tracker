# 지휘자 — 접수 (기획을 받아 이슈로)

사람의 첫 메시지가 이슈 번호나 FIELD-REPORT 절이 아니라 **요청 본문(기획)**이면 이 파일을 읽는다.
이슈 번호만 받고 흐름(작은 수정·설계)이 지정되지 않았을 때도 2절만 읽고 고른다.
`agents/COORDINATOR.md` 1절 1~4번을 마친 뒤, 1절 6번(Run 만들기) 전에 한다.

**묻지 않는다.** 무엇을 원하는지 자체가 불분명할 때만 사람에게 묻는다(예: "이거 고쳐줘"만 있고 대상이 없음).
양식, 흐름, PLAN 버전, 작업 ID는 아래 규칙으로 정하고 이슈와 PR에 적는다. 틀렸으면 사람이 PR에서 본다.

## 1. 이슈 만들기

1. **이미 있는지 본다.** 요청의 핵심 낱말로 `gh issue list --state open --search "<낱말> in:title" --json number,title`.
   같은 요청의 열린 이슈가 있으면 새로 만들지 않고 그 이슈를 쓴다. (같은 요청이 #23·#24로 두 번 만들어졌다)
2. **양식을 고른다** (`.github/ISSUE_TEMPLATE/`).

   | 양식 | 언제 |
   |---|---|
   | `1-improve.yml` 개선 | 이미 있는 기능이 불편하거나 틀렸다 |
   | `2-feature.yml` 새 기능 | 지금 없는 입력·화면·판정을 새로 붙인다 |
   | `3-restructure.yml` 구조 변경 | 저장 방식·백업·화면 구조처럼 뼈대를 바꾼다 |

3. **본문을 쓴다.** `.reports/issue-draft.md`에 쓰고 `--body-file`로 넘긴다.
   - 맨 위 한 줄: `접수: 지휘자 · 흐름: <작은 수정 | 설계> — <고른 이유 한 줄>`
   - 그 아래는 고른 양식의 칸 이름을 `### <칸 이름>` 제목으로 순서대로 쓴다. 요청에 없는 필수 칸은 `요청에 없음 — 설계자가 정한다`로 둔다.
   - 개선 양식의 "크기"는 2절의 결과(`작은 수정` 또는 `설계 필요`)를 쓴다.
   - 체크 칸(핵심 설계 결정 점검)은 **체크하지 않는다.** 판단은 설계자 몫이다. 구조 변경의 "README 결정을 뒤집는다" 승인은 사람만 한다.
   - 맨 끝에 `### 요청 원문` 절을 두고 사람의 메시지를 고치지 않고 그대로 붙인다.
4. `gh issue create --title "[<양식 이름>] <제목>" --label <양식 이름> --body-file .reports/issue-draft.md`
   라벨이 없다는 오류면 `--label` 없이 다시 만든다.
5. 이슈 번호를 사람에게 한 줄로 알리고 **기다리지 않고** 진행한다.

## 2. 흐름 고르기

**모르면 설계다.** 설계로 잘못 가면 토큰이 조금 더 들 뿐이지만, 작은 수정으로 잘못 가면 설계 검토 없이 규칙이 바뀐다.

작은 수정은 아래가 **모두** 맞을 때만이다.
- 사람이 "작은 수정"이라고 했거나, 요청이 문구 하나·버그 하나처럼 한 가지 사실만 바꾼다
- `agents/coordinator/SMALL.md` 1절의 나머지 조건(성공 기준, 저장 구조·시드·내보내기 형식·Gist·판정 규칙 무변경, 앱 주인이 정할 갈림길 없음)을 만족한다

사람이 흐름을 지정했으면 그대로 따른다.
그 뒤 작은 수정이면 `agents/coordinator/SMALL.md`, 설계면 `agents/coordinator/DESIGN.md`를 읽고 그 이슈로 진행한다.
설계의 PLAN 버전과 작업 ID는 DESIGN.md "PLAN 버전과 작업 ID"대로 정한다.

## 3. 이후

- 진행 파일(COORDINATOR.md 7절) 첫 줄에 `접수: 이슈 #<번호> (지휘자가 만듦)`을 적는다.
- PR 본문 머리 항목 맨 앞에 1절 3번의 `접수: … · 흐름: …` 줄을 그대로 넣는다(`Closes #<번호>`는 PR.md 2절대로).
