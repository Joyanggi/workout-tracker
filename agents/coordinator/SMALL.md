# 지휘자 — 작은 수정 (PLAN 없이)

문구 하나, 버그 하나처럼 설계서를 쓰는 비용이 수정보다 큰 일은 PLAN 없이 이슈를 설계서로 삼는다.
`agents/COORDINATOR.md`의 1~5절·7절을 그대로 따르고, PR은 `agents/coordinator/PR.md`를 따른다.

## 1. 작은 수정으로 해도 되는가

이슈를 `gh issue view <번호> --json title,body,labels`로 읽는다. 이슈는 문서라 읽어도 된다.
**아래가 모두 맞을 때만** 작은 수정이다. 하나라도 아니면 사람에게 "설계 작업으로 하자"고 알리고 멈춘다.

- 이슈에 **성공 기준**이 있다 (무엇이 보이거나 바뀌면 끝인지)
- 이슈 양식의 "크기"가 `작은 수정`이거나, 이슈 맨 위 접수 줄이 `흐름: 작은 수정`이거나(INTAKE.md), 사람이 "작은 수정으로"라고 지정했다
- 이슈가 저장 구조(Dexie 스키마), 시드 JSON, 내보내기 형식, Gist 백업을 바꾸자고 하지 않는다
- 이슈가 증량 판정·복귀·세트 계획처럼 **기록을 해석하는 규칙**을 바꾸자고 하지 않는다
- 이슈에 앱 주인이 정해야 할 갈림길(문구 후보 여러 개, 표시 위치 미정)이 없다

코드를 봐야 판단되는 조건은 구현자가 확인한다(IMPLEMENTER.md 8절). 구현자가 `중단(사람 필요)`와 "설계 필요"를 보고하면 그대로 사람에게 전한다.

## 2. 일꾼 배치

| 역할 | 에이전트 | 모델 | effort | 작업 트리 |
|---|---|---|---|---|
| 구현자 | claude | sonnet | medium | 새 작업 트리 `fix-<이슈 번호>` |
| 화면 검증자 | claude | sonnet | medium | 구현자의 작업 트리. 화면 변경이 있을 때만 (COORDINATOR.md 3절) |
| 리뷰어 | claude | opus | medium | 구현자의 작업 트리 (경로로 지정) |

리뷰어 effort를 medium으로 낮춘 것은 diff가 작아서다. 반려 규칙(COORDINATOR.md 3·4절)은 같다.
화면 검증 spec은 COORDINATOR.md 2절의 것에서 `<PLAN 파일>의 <작업 ID>`를 `이슈 #<번호>`로, 보고서 이름을 `screen-check-fix-<번호>.md`로 바꿔 쓴다.

## 3. spec

구현:
```
agents/IMPLEMENTER.md를 읽고 이슈 #<번호>를 8절(작은 수정)대로 진행해. 지휘자가 띄운 것이니 계획 보고 없이 진행해.
끝나면 7절의 네 줄 보고를 worker_done 요약으로 보내.
```

리뷰:
```
agents/REVIEWER.md를 읽고 이슈 #<번호>의 성공 기준으로 이 브랜치를 리뷰해(5절 작은 수정).
판정 전문을 worker_done 요약으로 보내.
```

## 4. 마무리

승인되면 PR.md대로 PR을 만든다. 머리 항목: `작은 수정 (PLAN 없음)`과 이슈 제목. 2절의 `Closes #<번호>`를 반드시 넣는다.
DEV-RECORD 대신 구현자가 쓴 `.reports/fix-<번호>-record.md`를 PR 본문 검증 항목 아래에 붙인다.
`package.json` 버전은 올리지 않는다. 다음 PLAN 버전에 함께 올라간다.

```
완료: 이슈 #<번호> <제목> (작은 수정)
<PR.md 5절의 공통 줄. 사람이 할 일: 화면 확인 → PR 머지>
```
