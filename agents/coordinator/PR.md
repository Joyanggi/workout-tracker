# 지휘자 — PR 만들기, 머지 기다리기, 정리

지휘자가 만드는 **모든 PR**(구현, 작은 수정, PLAN, 자동 승인으로 합친 PR)은 이 파일대로 한다.
PR 본문에 들어갈 "그 일만의 항목"은 각 파일(COORDINATOR·BATCH·DESIGN·SMALL)이 정하고, 나머지는 여기서 정한다.
(PR 관련 규칙은 이 파일 한 곳에만 둔다. 다른 파일에 다시 적지 않는다.)

## 1. PR 만들기

1. **브랜치 이름은 추측하지 않는다.** Orca가 `Joyanggi/` 같은 접두사를 붙이므로, 작업 트리에서 `git branch --show-current`로 실제 이름을 확인해 보고와 PR에 그 이름을 쓴다.
2. 본문은 파일로 쓴다: `.reports/pr-<대상>.md` (따옴표·줄바꿈이 셸에서 깨지지 않게). 항목은 2절.
3. `git push -u origin <브랜치>` → `gh pr create --base main --head <브랜치> --title "<제목>" --body-file .reports/pr-<대상>.md`
4. push나 `gh pr create`가 GitHub 서버 오류(5xx)로 실패하면 다시 시도한다. PR 생성은 다시 하기 전에 `gh pr list --head <브랜치>`로 이미 생겼는지 먼저 확인한다.
   기다릴 때는 `sleep`으로 명령을 시작하지 말고, 반복문 안에서 시도와 `sleep 60`을 함께 쓴다(최대 3번). 그래도 실패하면 사람에게 알리고 멈춘다.
5. 진행 파일에 PR 번호를 적는다.

**PR을 만든 뒤에는 그 브랜치에 push하지 않는다.** 머지 대기 중에 push하면 사람이 이미 본 내용과 머지되는 내용이 달라지고, 머지 직전 push는 빠진다(PR #16에서 일어났다).
더 고칠 게 생기면 머지된 뒤 새 브랜치에서 새 PR로 한다. 사람이 PR에서 고쳐달라고 하면 그때만 같은 브랜치에 push하고 PR에 댓글로 알린다.

## 2. PR 본문

순서대로 쓴다.

1. **그 일만의 머리 항목** (각 파일이 정한 것. 예: 지휘자가 접수한 일이면 맨 앞에 `접수: … · 흐름: …` 줄, 설계면 검토자, 자동 승인이면 "PLAN 포함")
2. 이슈가 있으면 `Closes #<번호>` (머지되면 이슈가 닫힌다)
3. PLAN 작업 ID (작은 수정이면 이슈 번호)
4. 검증: 구현자 보고의 `검증:` 줄 그대로 (`npm run check` 통과, 테스트 수, 결함 복원, 변이 점수)
5. 배포 영향: 시드 교체(`seedRevision`), 내보내기 형식 변화, 저장 구조 변화처럼 **머지하면 폰 앱에서 달라지는 것**. 없으면 "없음"
6. 리뷰어의 경미한 점 (없으면 "없음")
7. 사람이 화면에서 확인할 것: 화면 검증자 보고서의 "실기기에서 볼 것"과 DEV-RECORD의 실기기 확인 목록, 스크린샷 폴더(`docs/screenshots/<버전>/`). 없으면 "없음"
8. 경과: 진행 파일 표에서 `구현 <n>회 · 화면 검증 <n>회(반려 <n>) · 리뷰 <n>회(반려 <n>) · 걸린 시간 <첫 시작>~<마지막 끝>`
9. `## 토큰 사용` 절: `gh pr create` 직전에 `node scripts/token-usage.mjs --since "<진행 파일의 측정 시작>" >> .reports/pr-<대상>.md`로 붙인다. 출력을 고치지 않는다(맨 끝 주석은 규칙 정비가 읽는다).
   실패하면 `## 토큰 사용` 아래에 `측정 실패: <오류 첫 줄>`만 쓰고 규칙 메모에 적는다. PR을 만든 뒤 진행 파일의 `측정 시작`을 지금 시각으로 바꾼다(같은 세션에서 이어지는 다음 PR이 겹쳐 세지 않게).
10. 맨 끝에 `## 규칙 메모` 절 (3절)

## 3. 규칙 메모

이번 실행에서 **일이 계획대로 안 된 곳**을 한 줄씩 적는다. 없으면 "없음". 생기는 대로 진행 파일에 적어 두고 PR에 옮긴다.
`scripts/incidents.mjs`가 이 줄을 모아 같은 문제가 몇 번 나왔는지 세므로 모양을 지킨다.
```
- [분류] <단계>: <무슨 일> → <어떻게 넘겼는지> (키: <키>)
```
- **분류**(하나): `명령`(문법·권한·경로) · `환경`(설치·버전·OS·네트워크) · `일꾼`(띄우기·한도·보고 없음) · `규칙`(규칙 없음·틀림·충돌, 안전장치에 막힘) · `반려`(리뷰·화면 검증·설계 검토가 돌려보냄) · `검사`(CI·테스트·빌드 실패) · `사람`(사람이 끼어듦)
- **단계:** 접수 · 설계 · 설계 검토 · 구현 · 화면 검증 · 리뷰 · PR · 머지 대기 · 정리
- **키:** 같은 원인이면 같은 키. 키를 짓기 전에 `node scripts/incidents.mjs --keys`로 있는 키를 본다. 맞는 키가 있으면 그걸 쓰고, 없을 때만 영어 소문자와 하이픈 3~5낱말로 새로 만든다(예: `npm-lock-ci-version`). 키는 **원인**의 이름이다. 작업 ID(`qq4-…`)를 넣지 않는다. 원인을 추측할 수 있으면 `<무슨 일>`에 덧붙인다.
- 반려는 "고칠 것" 1번 항목의 요지로 한 줄 쓴다. 고칠 것이 여럿이면 원인이 다른 것만 줄을 나눈다.
- 예: `- [환경] PR: CI의 npm ci가 잠금 파일을 거부 → 사람이 Node 24로 올리라고 함 (키: npm-lock-ci-version)`

규칙 메모는 기록만 한다. 규칙 파일은 직접 고치지 않는다. 모인 메모는 규칙 정비(`agents/RULES-KEEPER.md`)에서 처리한다.
**PR 없이 멈추는 Run**(gate로 끝남, 사람이 그만두라고 함)은 진행 파일의 규칙 메모를 이슈에 `## 규칙 메모 (추가)` 댓글로 남긴다(`gh issue comment <번호> --body-file <파일>`). 이슈가 없으면 최종 보고에만 적는다.
PR을 만든 뒤에 생긴 일(머지 대기 중 문제, 정리 실패 등)은 최종 보고의 규칙 메모에 덧붙이고, 같은 내용을 `gh pr comment <PR 번호> --body-file <파일>`로 `## 규칙 메모 (추가)` 댓글로도 남긴다. 머지된 뒤에도 댓글은 달 수 있다.

## 4. 머지 기다리기

**먼저 CI를 본다.** PR을 만든 직후 `gh pr checks <PR 번호> --watch --fail-fast`를 Bash 타임아웃 600000으로 실행한다.
실패하면 실패한 검사 이름과 로그 끝(`gh run view <run ID> --log-failed 2>&1 | tail -30`)을 사람에게 알리고, 규칙 메모에 `[검사]`로 적는다. 브랜치에는 push하지 않는다(1절). 사람이 고쳐 달라고 하면 그때 고친다.
머지를 막는 필수 검사는 `ci` 하나다. `Security`(CodeQL·OSV)는 필수가 아니다. 그쪽만 실패했으면 무엇이 걸렸는지 한 줄로 알리고 머지 대기로 넘어간다. 머지할지는 사람이 정한다.

그다음 gate를 걸고 사람에게 알리되(5절 형식), 멈추지 않고 머지를 기다린다. 아래 명령을 Bash 타임아웃 600000으로 실행한다.
```
for i in $(seq 1 18); do s=$(gh pr view <PR 번호> --json state -q .state); [ "$s" != "OPEN" ] && echo $s && break; sleep 30; done
```
- `MERGED`: main 작업 트리에서 `git pull --ff-only`를 한 뒤 5절 정리로 간다. 그다음 그 일의 다음 단계로 간다.
- `CLOSED`: 사람에게 알리고 멈춘다.
- 여전히 `OPEN`: 같은 명령을 다시 실행한다. 합쳐서 2시간이 지나면 "PR 머지 대기 중"이라고 보고하고 멈춘다.
  나중에 사람이 "머지했어"라고 하면 새 세션에서 진행 파일을 읽고 이어서 한다.

## 5. 정리와 최종 보고

머지가 확인되면 **이번 Run이 만든 작업 트리를 지우고 그 로컬 브랜치를 삭제한다.**
- 작업 트리 삭제 명령은 orchestration 스킬이나 `orca-cli` 스킬에서 찾아 쓰고, 없으면 `git worktree remove <경로>`(강제 없이)를 쓴다.
- 브랜치는 `git branch -d <브랜치>`로 지운다. `-D`는 쓰지 않는다.
- 작업 트리 삭제가 `Permission denied`로 실패하면(Windows에서 그 폴더를 연 터미널·프로세스가 남아 있다) 다시 시도하지 않는다. 브랜치만 지우고, 남은 폴더 경로를 최종 보고의 `정리:` 줄에 적어 사람이 지우게 한다(세 번 일어났다).
- 이번 Run이 만들지 않은 작업 트리와 main 작업 트리는 건드리지 않는다.
- 진행 파일 끝에 `끝남`을 적는다.

최종 보고 공통 줄 (각 파일의 보고 양식 끝에 붙인다):
```
브랜치: <git branch --show-current로 확인한 실제 이름> (작업 트리: <이름>)
PR: <URL> (<MERGED | 머지 대기 중>)
경과: <2절 8번과 같은 줄>
정리: <지운 작업 트리·브랜치 목록. 못 지운 것은 이유와 함께>
규칙 메모: <3절. 없으면 "없음">
사람이 할 일: <그 일의 할 일>
```
