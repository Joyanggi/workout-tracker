# 지휘자 — 설계 작업

`agents/COORDINATOR.md`의 0·1·3·5절과 "기다리는 법"은 그대로 따른다. 이 파일은 2·4·6절을 대신한다.

서로 다른 회사의 모델 셋이 같은 설계서를 다룬다. 같은 회사 모델끼리는 놓치는 곳이 겹치기 때문이다.
검토자 둘은 무료 한도로 돌아서 Claude 한도를 쓰지 않는다.

## 일꾼 배치

| 순서 | 역할 | 에이전트 | 모델 | effort | 작업 트리 |
|---|---|---|---|---|---|
| 1 | 설계자 | claude | opus | high | **새 작업 트리** `plan-<PLAN 버전>`, 최신 `main`에서 |
| 2 | 검토자 ① | codex | 기본값 | 기본값 | 설계자와 같은 작업 트리 |
| 3 | 검토자 ② | antigravity | 기본값 | 기본값 | 설계자와 같은 작업 트리 |

### 검토자 선택

- 사람의 첫 메시지에 검토자 지정(예: "검토자: codex", "검토자: claude")이 있으면 그대로 따른다.
- 없으면 위 표대로 Codex와 Antigravity를 동시에 띄운다.
- 검토자가 보고 없이 끝나면 `orca orchestration worker-read`로 마지막 출력을 읽는다.
  - 사용량 한도(limit, quota, usage, rate limit 등)로 끝난 것이면, 그 자리를 **Claude 검토자**(sonnet·high, 새 세션)로 바꿔 같은 spec과 같은 PLAN 커밋 SHA로 띄운다. 보고 파일은 `.reports/<PLAN 버전>-claude.md`다. Claude 검토자는 최대 하나만 둔다.
  - 한도가 아닌 이유로 끝났으면 사람에게 알리고 멈춘다.
- 실제로 검토한 검토자와, 바꿨다면 그 사유를 적어둔다. PR 본문에 쓴다(아래 "자동 승인"·"사람에게 넘기기").

## 일꾼 운용

- 설계는 품질 차이가 가장 큰 단계라 opus·high를 쓴다. 대신 호출 횟수가 적다.
- 설계자가 끝나고 release한 뒤, 검토자 ①②를 **차례로가 아니라 동시에** 띄운다. 그 밖의 일꾼은 하나씩이다. **검토자끼리 서로의 결과를 전하지 않는다.**
- 설계자가 PLAN을 커밋하면 지휘자는 그 커밋 SHA(`git rev-parse HEAD`)를 적어두고, 두 검토자 spec에 똑같이 적는다.
- 검토자는 `npm test`와 `npm run build`를 돌리지 않고 읽기만 한다. 같은 작업 트리에서 동시에 돌아 빌드 결과물이 섞이지 않게 하려는 것이다.

## spec

설계자:
```
agents/DESIGNER.md를 읽고 설계해.
주제: <주제 원문> / PLAN 파일: <PLAN 파일> / 작업 ID: <접두사>
끝나면 5절 형식의 보고를 worker_done 요약으로 보내.
```

검토자 (①②같은 문장, 동시에 띄운다. `<이름>`만 codex / antigravity / claude로 바꾼다):
```
CLAUDE.md와 agents/PLAN-REVIEWER.md를 읽고 <PLAN 파일>을 설계 검토해.
원래 문제는 <주제 원문>이야. 검토 커밋은 <SHA>야. 레포 파일은 고치지 마.
보고는 PLAN-REVIEWER.md 3절대로 .reports/<PLAN 버전>-<이름>.md에 쓰고 --report-path로 알려줘.
```

검토자의 판정과 "고칠 것"은 그 보고 파일에서 읽는다. 보고 파일은 문서라 읽어도 된다.

**검토자가 worker_done 없이 종료돼도, 보고 파일의 둘째 줄 SHA가 이번 PLAN 커밋과 같고 첫 줄에 판정이 있을 때만 정상 완료로 본다.**
Codex는 샌드박스 안에서 `orca` 명령을 실행하지 못해 완료 신호를 못 보낼 때가 있다.
이때 Orca가 "보고 없이 종료" 알림을 보내니, 그 알림을 받으면 보고 파일부터 확인한다.
조건을 만족하면 gate를 걸지 말고 일꾼을 release한 뒤 다음 단계로 간다. 파일이 없거나 SHA·판정이 맞지 않으면 사람에게 알리고 멈춘다(COORDINATOR.md 3절).

지휘자는 Orca 작업 트리 폴더를 읽을 수 있게 `--add-dir`로 띄워져 있어야 한다.
읽기가 거부되면 사람에게 "`--add-dir C:\Users\jyg66\orca\workspaces`로 다시 띄워달라"고 알린다.

## 검토 반영 (자동)

검토가 둘 다 끝나면 **설계자에게 반영 판단을 맡긴다.** 지휘자는 어느 지적이 맞는지 판단하지 않는다.
검토자가 한도 초과로 실패하면 "검토자 선택"대로 Claude 검토자로 바꾼다. 바꿀 수 없으면 그 검토자는 건너뛰고 남은 보고만 넘긴다.

같은 작업 트리에서 설계자를 다시 띄운다.
```
agents/DESIGNER.md 6절대로 두 검토를 반영해 <PLAN 파일>을 고쳐.
검토 보고: .reports/<PLAN 버전>-<이름>.md (실제로 검토한 검토자 것만, 예: codex·antigravity)
끝나면 5절 형식으로 보고해.
```

## 자동 승인

설계자의 보고를 받으면 아래 네 조건을 확인한다. **모두 맞으면** PLAN PR을 만들지 않고 바로 구현 흐름(`agents/coordinator/BATCH.md`)으로 넘어간다.
- **Codex와 Antigravity가 모두 검토했음.** 그 밖의 조합(Claude 검토자가 끼었거나 한쪽이 빠진 경우)이면 자동 승인하지 않고 PLAN PR을 올린다.
- 두 검토자의 판정이 모두 "그대로 진행 가능"
- 설계자가 기각한 지적이 없음
- 설계자 보고의 "사람에게 남은 것"이 없음

구현은 plan 브랜치를 기준으로 한다. 같은 작업 트리에서 이어서 할지, plan 브랜치에서 새 작업 트리를 만들지는 `orca skills get orchestration --full`을 읽고 가능한 방법을 고른다.
최종 구현 PR은 PLAN 커밋과 구현 커밋을 함께 담는다. PR 본문 맨 위에 실제로 검토한 검토자(바꿨다면 그 사유 포함), "PLAN 포함" 표시, "설계자가 대신 정한 것" 목록을 적는다.

조건이 하나라도 맞지 않으면 아래 "사람에게 넘기기"대로 PLAN PR을 만든다.

## 사람에게 넘기기

자동 승인 조건이 맞지 않으면 gate를 걸고 멈춘다. 아래를 원문 그대로 전한다.

```
설계 확정 후보: <PLAN 파일> (작업 <접두사>1~<n>)
검토자: <실제로 검토한 검토자. 바꿨다면 "codex → claude (사유: 한도 초과)" 식으로>
브랜치: <브랜치 이름>
반영한 지적: <설계자 보고의 반영 목록 원문>
기각한 지적: <설계자 보고의 기각 목록과 이유 원문>
설계자가 정한 것: <"사람이 정할 것" 중 설계자가 추천안으로 확정한 항목 원문>
사람에게 남은 것: <없으면 "없음">
PR: <gh pr create가 돌려준 URL>
사람이 할 일: PLAN을 읽고 기각·확정에 이견이 있으면 알려주기. 없으면 PR 머지
```

자동 승인되지 않으면(설계자 보고를 받은 시점) PLAN 문서도 구현과 같은 방식으로 PR로 올리고 멈춘다.
push 전에 `git branch --show-current`로 실제 브랜치 이름을 확인하고(규칙 형식으로 추측하지 않는다),
작업 브랜치를 push한 뒤 `gh pr create`로 PR을 만든다. PR 본문 맨 위에 실제로 검토한 검토자(바꿨다면 사유)를 쓰고, 이어서 위 보고 내용을 쓴다. PR은 머지하지 않는다.

사람이 이견을 주면 같은 작업 트리에서 설계자를 다시 띄워 DESIGNER.md 4절대로 고치게 한다.

## 마무리

자동 승인됐다면 이 절은 건너뛴다. PLAN PR을 올렸다면 COORDINATOR.md "기다리는 법"의 PR 머지 대기로 기다린다.
PLAN PR이 머지되면 **사람에게 묻지 않고** 그 PLAN의 구현 순서대로 구현 흐름(`agents/coordinator/BATCH.md`)을 시작한다.
`CLOSED`이거나 사람이 이견을 주면 위 절차대로 멈추거나 설계를 고친다.
