# 지휘자 — 여러 작업 이어서 구현

`agents/COORDINATOR.md`의 1~5절("기다리는 법" 포함)을 작업마다 그대로 따른다. 일꾼을 띄울 때마다 턴을 끝내지 말고 그 방식으로 기다린다. 이 파일은 거기에 더할 것과 6절(마무리)을 대신하는 것이다.

## 대상 고르기

1. PLAN의 작업 목록과 "구현 순서" 절, `docs/DEV-RECORD-<PLAN 버전>.md`(있으면)의 완료 기록만 읽는다.
   이건 문서라서 읽어도 된다. 코드는 여전히 열지 않는다. 두 문서 모두 `grep -n`으로 필요한 절만 본다.
2. 기록에 완료로 적힌 작업은 뺀다. 애매하면 넣는다. 구현자가 시작 전 확인에서 "이미 구현됨"으로 걸러낸다.
3. 순서는 PLAN의 "구현 순서" 절을 따른다.
4. 사람에게 목록과 순서를 한 줄로 알리고 **기다리지 않고 바로 시작한다.**

## 작업 트리와 브랜치

- 작업 트리는 **하나만** 만든다. 브랜치는 `feature/<PLAN 버전>` (Orca 접두사 허용).
- 모든 작업을 이 브랜치에 순서대로 쌓는다. 앞 작업이 승인돼야 다음 작업을 시작한다("묶음"이면 앞 작업의 구현이 끝나면 시작한다).
- DESIGN.md "자동 승인"으로 넘어왔다면 plan 브랜치를 기준으로 하고, PR 본문 맨 위에 "PLAN 포함"과 "설계자가 대신 정한 것" 목록을 적는다.
- 마지막 작업이 승인되면 지휘자가 이 브랜치를 push하고 PR 하나를 만들고 머지를 기다린다. 머지는 사람이 한다. 지휘자와 일꾼은 PR을 머지하지 않는다.

## 리뷰 단위

PLAN "구현 순서와 검증" 절의 `리뷰 단위:`를 따른다. 없으면 "작업별"이다.

- **작업별:** 아래 "작업마다 더할 것"과 COORDINATOR.md 그대로, 작업마다 구현자 → 리뷰어 순서로 돈다.
- **묶음:** 작업마다 구현자만 돌린다(리뷰어는 띄우지 않는다). 구현자 `완료`/`이미 구현됨`이면 release하고 바로 다음 작업으로 간다.
  마지막 작업 뒤에 리뷰어를 한 번 띄워 전체를 리뷰한다. 리뷰 범위는 첫 작업의 시작 커밋부터다(`리뷰 범위: <첫 시작 커밋>..HEAD`).
  반려되면 "고칠 것"에 해당하는 작업만 같은 작업 트리에서 다시 구현하고(COORDINATOR.md 4절), 이어서 리뷰어를 다시 띄운다. 두 번째 반려는 멈추는 조건이다.

## 작업마다 더할 것

- 구현자를 띄우기 직전에 `git rev-parse HEAD`로 **시작 커밋**을 적어둔다. 위치 기록일 뿐 코드를 읽는 게 아니다.
- 리뷰어 spec 끝에 `리뷰 범위: <시작 커밋>..HEAD`를 붙인다. 안 붙이면 리뷰어가 승인된 앞 작업까지 다시 읽는다.

## 승인 뒤에 붙이는 커밋

- 리뷰 승인 뒤 붙이는 기록·버전 커밋은 `docs/`와 `package.json`만 바꾼다.
- 리뷰어의 경미한 점을 고치느라 `src/`를 바꿔야 하면(테스트 파일과 주석 포함) 그 커밋도 리뷰어에게 다시 맡겨 승인받은 뒤 PR에 넣는다.

## 기억을 줄인다

작업 하나가 승인되면 그 작업에 대해 기억할 것은 한 줄뿐이다.

```
<ID> 승인 · 커밋 <해시> · 경미한 점 <n>건
```

앞 작업의 보고 전문을 다음 작업 spec에 옮기지 않는다.

## 멈추는 조건

아래 중 하나라도 생기면 **전체를 멈추고** gate를 건다. 남은 작업은 시작하지 않는다.

- 구현자 `중단(사람 필요)` 또는 리뷰어 `사람 필요`
- 같은 작업의 두 번째 반려
- 일꾼이 보고 없이 종료
- 사용 한도 초과

멈출 때는 아래 진행표와 멈춘 이유를 전한다.
사람이 "이어서 진행해"라고 하면 **새 세션**에서 이 파일을 다시 읽고, 같은 브랜치의 남은 작업부터 시작한다.

## 마무리 보고

마지막 작업이 승인되면 push 전에 `git branch --show-current`로 실제 브랜치 이름을 확인한다(규칙 형식으로 추측하지 않는다).
그 브랜치를 push하고 `gh pr create`로 PR 하나를 만든다. PR 본문에 작업별 검증 결과와 리뷰어의 경미한 점을 적는다.
COORDINATOR.md "기다리는 법"의 PR 머지 대기로 기다리다가, PR이 머지되면 main 작업 트리에서 `git pull`을 하고, 작업 트리와 로컬 브랜치를 정리한 뒤(COORDINATOR.md의 `MERGED` 항목) 아래 최종 보고를 하고 끝낸다.

```
완료: <PLAN 파일> (<n>개 작업)
브랜치: <git branch --show-current로 확인한 실제 이름> (작업 트리: <이름>)
PR: <gh pr create가 돌려준 URL>

| 작업 | 결과 | 커밋 | 구현 | 리뷰(반려) | 경미한 점 |
|---|---|---|---|---|---|
| <ID>1 | 승인 | <해시> | 1회 | 1회(0) | 없음 |

정리: <지운 작업 트리·브랜치 목록. 못 지운 것은 이유와 함께>
규칙 메모: <규칙과 실제가 어긋난 점을 한 줄씩. 없으면 "없음". 규칙 파일은 직접 고치지 않는다>
사람이 할 일: DEV-RECORD의 실기기 확인 목록 (PR은 머지됨)
```
