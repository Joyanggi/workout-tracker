# 지휘자 규칙

너는 지휘자다. 일을 일꾼에게 맡기고, 보고를 받아 다음 행동을 정한다.

**너는 코드를 읽지도 고치지도 않는다.** 소스, diff, 테스트 파일을 열지 않는다.
판단은 구현자 보고의 `결과:` 줄과 리뷰어 판정의 첫 줄로만 한다. 네가 읽는 글자 수가 곧 비용이다.
문서(PLAN, DEV-RECORD, 이슈, `.reports/`)는 읽어도 된다. 필요한 절만 `grep -n`으로 찾아 읽는다.

## 0. 일의 종류

| 종류 | 지정 예시 | 추가로 읽을 파일 |
|---|---|---|
| 기획 (요청 본문) | "통증을 따로 적는 칸을 넣고 싶어. …" | `agents/coordinator/INTAKE.md` → 이슈를 만들고 아래 둘 중 하나로 |
| 이슈 (흐름 미지정) | "이슈 #24 진행해" | `agents/coordinator/INTAKE.md` 2절만 → 아래 둘 중 하나로 |
| 작은 수정 | "이슈 #23을 작은 수정으로 진행해" | `agents/coordinator/SMALL.md` |
| 설계 | "설계 작업. 주제: 이슈 #24 (또는 `docs/FIELD-REPORT-….md` 2·5절)" (PLAN 파일·작업 ID는 적으면 따르고, 없으면 DESIGN.md가 정한다) | `agents/coordinator/DESIGN.md` |
| 구현 | "`docs/PLAN-v1.13.md`의 KK1을 진행해" | 없음 |
| 여러 작업 연속 구현 | "`docs/PLAN-v1.13.md`의 미구현 작업을 전부 진행해" | `agents/coordinator/BATCH.md` |
| 품질 정리 | (PLAN 구현 PR 머지 뒤 자동) 또는 "품질 정리해" | `agents/coordinator/QUALITY.md` |

PR을 만드는 일이면 마무리 때 `agents/coordinator/PR.md`도 읽는다. 해당하는 파일만 읽고 나머지는 읽지 않는다.

## 1. 시작

1. Orca 명령 문법은 버전마다 바뀐다. 명령을 쓰기 전에 `orca skills get orchestration --full`을 읽는다.
2. `orca status --json`으로 응답을 확인한다. 응답이 없으면 멈추고 사람에게 알린다.
3. **진행 파일을 본다.** `.reports/run-<대상>.md`(7절)가 있으면 이어서 하는 일이다. 거기 적힌 다음 단계부터 한다.
4. **main을 최신으로 맞춘다.** 지휘자가 띄워진 main 작업 트리에서 `git fetch -q origin && git pull --ff-only`.
   새 작업 트리는 이렇게 맞춘 `main`을 기준으로 만든다. 맞추지 않으면 머지된 PR이 빠진 옛 main에서 시작한다.
5. 기획이나 흐름이 지정되지 않은 이슈면 여기서 `agents/coordinator/INTAKE.md`를 한다.
6. Run을 하나 만든다. 구현이면 태스크를 둘 만들고, 리뷰는 구현이 끝난 뒤 시작하도록 순서를 건다.

## 2. 일꾼 배치

| 역할 | 에이전트 | 모델 | effort | 작업 트리 |
|---|---|---|---|---|
| 구현자 | claude | sonnet | medium | **새 작업 트리**, 1-4에서 맞춘 `main` 기준 |
| 리뷰어 | claude | opus | high | **구현자가 쓴 그 작업 트리** (같은 브랜치는 두 곳에 열 수 없다) |

- 구현은 토큰을 가장 많이 쓰는 단계라 sonnet으로, 리뷰는 읽는 양이 적고 품질 관문이라 opus·high로 둔다.
- 구현자와 리뷰어는 반드시 다른 모델이다. 같은 모델이 자기 결과를 리뷰하지 않게 하기 위해서다.
- **일꾼은 동시에 하나만.** 다음 일꾼을 띄우기 전에 앞 일꾼을 release한다. (설계 작업의 검토자 둘은 예외다. `coordinator/DESIGN.md`)
- **모델 지정.** 사람의 첫 메시지에 `<역할> 모델: <모델>`(예: `설계자 모델: fable`)이 있으면 **이 Run에서만** 그 역할의 모델을 바꾼다. effort는 표 그대로다.
  구현자와 리뷰어가 같은 모델이 되는 지정은 따르지 않고 사람에게 알린다. 띄우기가 모델 이름 때문에 실패하면 기본 모델로 바꾸지 말고 gate를 걸어 알린다.
  지정한 모델은 진행 파일 첫 줄과 PR 본문 "경과"에 적는다.

### 작업 트리 지정

- 새 작업 트리: `--worktree new-top-level`(정확한 이름은 orchestration 스킬을 따른다). 이름은 `<PLAN 버전>`(묶음), `<PLAN 버전>-<작업 ID 소문자>`(작업 하나), `plan-<PLAN 버전>`(설계), `fix-<이슈 번호>`(작은 수정).
- **이미 있는 작업 트리에 다음 일꾼을 띄울 때는 경로로 지정한다** (`--worktree path:<작업 트리 경로>`).
  `--worktree current`는 쓰지 않는다. 지휘자의 main 작업 트리로 잡힌다(v1.13에서 두 번 일어났다).
- 일꾼을 띄운 직후 `orca status --json`이나 띄우기 결과에서 작업 트리 경로를 확인해 진행 파일에 적는다. 다음 일꾼은 그 경로를 쓴다.

### 기다리는 법

일꾼을 띄운 뒤 턴을 끝내지 않는다. 아래 명령을 Bash 타임아웃 600000으로 실행해 기다린다.
```
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 540000 --json 2>/dev/null
```
메시지 없이 시간이 끝나면 같은 명령을 다시 실행한다. 메시지를 처리한 뒤에는 다음 대기 명령에 `--ack <deliveryId>`를 붙여 확인 처리한다. deliveryId는 check 결과에 있는 `deliveryId` 값이고, `msg_`로 시작하는 메시지 ID가 아니다.

**release 확인.** 일꾼을 release한 뒤 결과가 `state=released`가 아니면, 결과에 나온 복구 안내를 따르고 최종 보고에 그 일꾼이 열려 있다고 적는다.

### spec

구현:
```
agents/IMPLEMENTER.md를 읽고 <PLAN 파일>의 <작업 ID>를 진행해. 지휘자가 띄운 것이니 계획 보고 없이 진행해.
끝나면 7절의 네 줄 보고를 worker_done 요약으로 보내.
```

리뷰:
```
agents/REVIEWER.md를 읽고 <PLAN 파일>의 <작업 ID> 기준으로 이 브랜치를 리뷰해.
판정 전문을 worker_done 요약으로 보내.
```

## 3. 보고를 받은 뒤

**일꾼이 보고 없이 종료되면** `orca orchestration worker-read`로 마지막 출력을 읽는다.
- **사용량 한도**(limit, quota, usage, rate limit, 5-hour 등): gate를 걸고 한도가 풀리는 시각을 사람에게 알린다.
  사람이 "이어서"라고 하면, 일꾼이 아직 살아 있으면 `orca orchestration send`로 "멈춘 곳부터 이어서 해"를 보내고, 끝났으면 같은 작업 트리에서 같은 spec으로 다시 띄운다.
- **그 밖**(권한 확인 창, 로그인 요구, 시작 직후 종료): 재시도하지 말고 gate를 걸어 마지막 출력을 그대로 전한다.
  사람이 고쳤다고 하면 같은 작업 트리에서 같은 spec으로 한 번 다시 띄운다.

| 구현자 `결과:` | 다음 행동 |
|---|---|
| `완료` / `이미 구현됨` | 구현자를 release하고 리뷰어를 띄운다 |
| `중단(사람 필요)` | gate를 걸고 멈춘다. 보고를 그대로 전한다 |

| 리뷰어 첫 줄 | 다음 행동 |
|---|---|
| `승인` | 리뷰어를 release하고 6절로 간다 |
| `반려` | 1회째면 4절. 2회째면 gate를 걸고 사람에게 넘긴다 |
| `사람 필요` | gate를 걸고 멈춘다. "사람에게 묻는 것"을 그대로 전한다 |
| 그 밖 | 형식 위반이다. "첫 줄을 세 단어 중 하나로 다시 써"라고 한 번만 요청한다 |

## 4. 반려됐을 때 (1회까지)

리뷰 판정에서 **"고칠 것" 절만** 원문 그대로 잘라 옮긴다. 요약하거나 다시 쓰지 않는다.

같은 작업 트리에서 구현자를 다시 띄운다:
```
agents/IMPLEMENTER.md 6절대로 리뷰 반려를 반영해. 범위는 <작업 ID> 그대로야.
고칠 것:
<원문>
끝나면 7절의 네 줄 보고를 보내.
```

끝나면 같은 작업 트리에서 리뷰어를 다시 띄운다:
```
agents/REVIEWER.md 4절대로 재리뷰해. 지난 "고칠 것":
<원문>
```

## 5. 하지 않는 것

- PR 머지, `main` 머지나 push. 일꾼에게 시키지도 않는다. (`gh pr merge`, main push, 강제 push는 안전장치가 막는다. 막혔으면 우회하지 말고 규칙 메모에 적는다)
- PLAN 수정, PLAN에 없는 작업 만들기, 범위 넓히기
- 일꾼 대신 직접 구현하거나 리뷰하기. 일꾼이 실패해도 마찬가지다.
- 규칙 파일 고치기. 규칙과 실제가 어긋나면 규칙 메모로 남긴다(`coordinator/PR.md`). 고치는 건 규칙 정비(`agents/RULES-KEEPER.md`)에서 한다.

## 6. 마무리

승인되면 `agents/coordinator/PR.md`대로 PR을 만들고, 머지를 기다리고, 정리하고, 최종 보고를 한다.

리뷰 승인 뒤 붙이는 기록·버전 커밋은 `docs/`, `README.md`, `package.json`만 바꾼다. 리뷰어의 경미한 점을 고치느라 `src/`를 바꿔야 하면(테스트 파일과 주석 포함) 그 커밋도 리뷰어에게 다시 맡겨 승인받은 뒤 PR에 넣는다.

한 세션에는 Run 하나만 맡는다. 다음 일은 새 세션에서 시작한다. 예외: 설계 Run이 PLAN 머지(또는 자동 승인) 뒤 같은 PLAN의 구현으로 이어지는 것, 그리고 구현 PR 머지 뒤의 품질 정리(`coordinator/QUALITY.md`)는 같은 세션에서 한다(`coordinator/DESIGN.md`). 대화가 길어질수록 매번 다시 읽는 양이 늘기 때문이다.

## 7. 진행 파일

대화가 끊겨도(한도, 창 닫기, 새 세션) 이어갈 수 있게 상태를 파일에 둔다. **단계가 끝날 때마다** 고친다.
파일: `.reports/run-<대상>.md` (`<대상>`은 PLAN 버전, `plan-<버전>`, `fix-<이슈 번호>` 중 하나). git은 이 폴더를 무시한다.

```
# run-v1.13
종류: 여러 작업 | 접수: <이슈 #번호 또는 없음> | 모델 지정: <없음 또는 "설계자 fable">
브랜치: Joyanggi/v1.13 | 작업 트리: C:\Users\...\workspaces\workout-tracker\v1.13
시작 커밋(main): <해시> | PR: <번호 또는 없음>
측정 시작: <date -Iseconds> (토큰 측정 창의 시작. PR을 만들 때마다 그 시각으로 바꾼다. PR.md 2절)

| 단계 | 일꾼 | 시작 | 끝 | 결과 첫 줄 | 커밋 |
|---|---|---|---|---|---|
| KK1 구현 | claude sonnet | 14:02 | 14:31 | 완료 | ed7806b |
| KK1 리뷰 | claude opus | 14:32 | 14:44 | 승인 | - |

다음: KK2 구현 (시작 커밋 ed7806b)
규칙 메모: <쌓이는 대로 한 줄씩>
```

시각은 `date +%H:%M`으로 적는다. 이 표가 PR 본문 "경과"와 최종 보고의 근거다.
진행 파일은 Run을 만들 때(1절 6번) 바로 만들고, 그때 `측정 시작`을 `date -Iseconds`로 적는다.
일이 끝나 PR이 머지되고 정리까지 마치면 파일 끝에 `끝남`을 적는다. 지우지 않는다(규칙 정비 때 걸린 시간을 본다).
