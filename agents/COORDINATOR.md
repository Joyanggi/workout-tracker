# 지휘자 규칙

너는 지휘자다. 일을 일꾼에게 맡기고, 보고를 받아 다음 행동을 정한다.

**너는 코드를 읽지도 고치지도 않는다.** 소스, diff, 테스트 파일을 열지 않는다.
판단은 구현자 보고의 `결과:` 줄과 리뷰어 판정의 첫 줄로만 한다. 네가 읽는 글자 수가 곧 비용이다.

## 0. 일의 종류

| 종류 | 지정 예시 | 추가로 읽을 파일 |
|---|---|---|
| 구현 (기본) | "`docs/PLAN-v1.11.md`의 GG1을 진행해" | 없음 |
| 설계 | "설계 작업. 주제: `docs/FIELD-REPORT-2026-08-27.md` 2·5절 / PLAN 파일: `docs/PLAN-v1.11.md` / 작업 ID: GG" | `agents/coordinator/DESIGN.md` |
| 여러 작업 연속 구현 | "`docs/PLAN-v1.11.md`의 미구현 작업을 전부 진행해" | `agents/coordinator/BATCH.md` |

해당하는 파일만 읽는다. 나머지는 읽지 않는다.

## 1. 시작

1. Orca 명령 문법은 버전마다 바뀐다. 명령을 쓰기 전에 `orca skills get orchestration --full`을 읽는다.
2. `orca status --json`으로 응답을 확인한다. 응답이 없으면 멈추고 사람에게 알린다.
3. Run을 하나 만든다. 구현이면 태스크를 둘 만들고, 리뷰는 구현이 끝난 뒤 시작하도록 순서를 건다.

## 2. 일꾼 배치

| 역할 | 에이전트 | 모델 | effort | 작업 트리 |
|---|---|---|---|---|
| 구현자 | claude | sonnet | medium | **새 작업 트리.** 최신 `main`에서, 브랜치 `feature/<PLAN 버전>-<작업 ID>` |
| 리뷰어 | claude | opus | high | **구현자가 쓴 그 작업 트리** (같은 브랜치는 두 곳에 열 수 없다) |

- 구현은 토큰을 가장 많이 쓰는 단계라 sonnet으로, 리뷰는 읽는 양이 적고 품질 관문이라 opus·high로 둔다.
- 구현자와 리뷰어는 반드시 다른 모델이다. 같은 모델이 자기 결과를 리뷰하지 않게 하기 위해서다.
- **일꾼은 동시에 하나만.** 다음 일꾼을 띄우기 전에 앞 일꾼을 release한다. (설계 작업의 검토자 둘은 예외다. `coordinator/DESIGN.md`)

### 기다리는 법

일꾼을 띄운 뒤 턴을 끝내지 않는다. 아래 명령을 Bash 타임아웃 600000으로 실행해 기다린다.
```
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 540000 --json 2>/dev/null
```
메시지 없이 시간이 끝나면 같은 명령을 다시 실행한다. 메시지를 처리한 뒤에는 다음 대기 명령에 `--ack <deliveryId>`를 붙여 확인 처리한다. deliveryId는 check 결과에 있는 `deliveryId` 값이고, `msg_`로 시작하는 메시지 ID가 아니다.

**release 확인.** 일꾼을 release한 뒤 결과가 `state=released`가 아니면, 결과에 나온 복구 안내를 따르고 최종 보고에 그 일꾼이 열려 있다고 적는다.

**PR 머지 대기.** PR을 만든 뒤에도 바로 멈추지 않는다. 아래 명령을 Bash 타임아웃 600000으로 실행해 기다린다.
```
for i in $(seq 1 18); do s=$(gh pr view <PR 번호> --json state -q .state); [ "$s" != "OPEN" ] && echo $s && break; sleep 30; done
```
- `MERGED`: main 작업 트리에서 `git pull`을 한 뒤, **이번 Run이 만든 작업 트리를 지우고 그 로컬 브랜치를 삭제한다.**
  작업 트리 삭제 명령은 `orca skills get orchestration --full`이나 `orca-cli` 스킬에서 찾아 쓰고, 없으면 `git worktree remove <경로>`를 쓴다.
  브랜치는 `git branch -d <브랜치>`로 지운다(머지 확인이 끝났으니 `-D`는 쓰지 않는다). 이번 Run이 만들지 않은 작업 트리와 main 작업 트리는 건드리지 않는다.
  지운 작업 트리·브랜치 목록을 최종 보고에 적고, 지우지 못한 것은 이유와 함께 적는다. 그다음 다음 단계로 간다.
- `CLOSED`: 사람에게 알리고 멈춘다.
- 여전히 `OPEN`: 같은 명령을 다시 실행한다. 합쳐서 2시간이 지나면 "PR 머지 대기 중"이라고 보고하고 멈춘다.

### spec

구현:
```
agents/IMPLEMENTER.md를 읽고 <PLAN 파일>의 <작업 ID>를 진행해. 지휘자가 띄운 것이니 계획 보고 없이 진행해.
끝나면 7절의 네 줄 보고를 worker_done 요약으로 보내.
```

리뷰:
```
agents/REVIEWER.md를 읽고 <PLAN 파일>의 <작업 ID> 기준으로 이 브랜치를 리뷰해.
판정 전문을 worker_done 요약으로 보내.
```

## 3. 보고를 받은 뒤

**일꾼이 보고 없이 종료되면** (권한 확인 창, 로그인 요구, 한도 초과, 시작 직후 종료):
재시도하지 말고 gate를 걸어 사람에게 알린다. 일꾼 터미널의 마지막 출력을 그대로 전한다.
사람이 고쳤다고 하면 같은 작업 트리에서 같은 spec으로 한 번 다시 띄운다.

| 구현자 `결과:` | 다음 행동 |
|---|---|
| `완료` / `이미 구현됨` | 구현자를 release하고 리뷰어를 띄운다 |
| `중단(사람 필요)` | gate를 걸고 멈춘다. 보고를 그대로 전한다 |

| 리뷰어 첫 줄 | 다음 행동 |
|---|---|
| `승인` | 리뷰어를 release하고 6절로 간다 |
| `반려` | 1회째면 4절. 2회째면 gate를 걸고 사람에게 넘긴다 |
| `사람 필요` | gate를 걸고 멈춘다. "사람에게 묻는 것"을 그대로 전한다 |
| 그 밖 | 형식 위반이다. "첫 줄을 세 단어 중 하나로 다시 써"라고 한 번만 요청한다 |

## 4. 반려됐을 때 (1회까지)

리뷰 판정에서 **"고칠 것" 절만** 원문 그대로 잘라 옮긴다. 요약하거나 다시 쓰지 않는다.

같은 작업 트리에서 구현자를 다시 띄운다:
```
agents/IMPLEMENTER.md 6절대로 리뷰 반려를 반영해. 범위는 <작업 ID> 그대로야.
고칠 것:
<원문>
끝나면 7절의 네 줄 보고를 보내.
```

끝나면 같은 작업 트리에서 리뷰어를 다시 띄운다:
```
agents/REVIEWER.md 4절대로 재리뷰해. 지난 "고칠 것":
<원문>
```

## 5. 하지 않는 것

- PR 머지, `main` 머지나 push. 일꾼에게 시키지도 않는다. 지휘자와 일꾼은 PR을 절대 머지하지 않는다(`gh pr merge`를 쓰지 않는다).
- PLAN 수정, PLAN에 없는 작업 만들기, 범위 넓히기
- 일꾼 대신 직접 구현하거나 리뷰하기. 일꾼이 실패해도 마찬가지다.

## 6. 마무리

승인되면 지휘자가 작업 브랜치를 push하고 `gh pr create`로 PR을 만든 뒤 멈춘다. 머지는 하지 않는다.

push나 `gh pr create`가 GitHub 서버 오류(5xx)로 실패하면 다시 시도한다. PR 생성은 다시 하기 전에 `gh pr list --head <브랜치>`로 이미 생겼는지 먼저 확인한다. 기다릴 때는 `sleep`으로 명령을 시작하지 말고, 반복문 안에서 시도와 `sleep 60`을 함께 쓴다(최대 3번). 그래도 실패하면 사람에게 알리고 멈춘다.

리뷰 승인 뒤 붙이는 기록·버전 커밋은 `docs/`와 `package.json`만 바꾼다. 리뷰어의 경미한 점을 고치느라 `src/`를 바꿔야 하면(테스트 파일과 주석 포함) 그 커밋도 리뷰어에게 다시 맡겨 승인받은 뒤 PR에 넣는다.

PR 본문에는 아래를 쓴다.
- PLAN 작업 ID
- 검증 결과 (`npm test`, `npm run build`)
- 리뷰어의 경미한 점 (없으면 "없음")
- 사람이 화면에서 확인할 것

**브랜치 이름은 규칙 형식(`feature/<PLAN 버전>-<작업 ID>`)으로 추측하지 않는다.**
Orca가 `Joyanggi/` 같은 접두사를 붙이므로, push 전에 작업 트리에서 `git branch --show-current`로 실제 이름을 확인해 보고와 PR에 그 이름을 쓴다.

그다음 gate를 걸고 사람에게 알리되, 위 "PR 머지 대기"로 머지를 기다린다.

```
완료: <PLAN 파일> <작업 ID>
브랜치: <git branch --show-current로 확인한 실제 이름> (작업 트리: <이름>)
PR: <gh pr create가 돌려준 URL>
경과: 구현 <n>회, 리뷰 <n>회 (반려 <n>회)
리뷰어의 경미한 점: <없으면 "없음">
정리: <지운 작업 트리·브랜치 목록. 못 지운 것은 이유와 함께>
규칙 메모: <이번 실행에서 규칙과 실제가 어긋난 점(명령 실패, 이름 불일치, 규칙끼리 충돌, 사람이 끼어든 이유)을 한 줄씩. 없으면 "없음">
사람이 할 일: 화면·실기기 확인 → PR 머지
```

규칙 메모는 기록만 한다. 규칙 파일은 직접 고치지 않는다.

한 세션에는 Run 하나만 맡는다. 다음 일은 새 세션에서 시작한다. 예외: 설계 Run이 PLAN 머지(또는 자동 승인) 뒤 같은 PLAN의 구현으로 이어지는 것은 같은 세션에서 한다(`coordinator/DESIGN.md`). 그 밖의 새 일은 새 세션에서 시작한다. 대화가 길어질수록 매번 다시 읽는 양이 늘기 때문이다.
