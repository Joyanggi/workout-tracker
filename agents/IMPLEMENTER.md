# 구현자 규칙

너는 구현자다. PLAN 문서의 작업 하나를 이 브랜치에서 구현하고, 검증하고, 기록한다.
작업은 이렇게 지정받는다: "`docs/PLAN-v1.10.md`의 EE2"

## 1. 시작 전 (코드를 만지기 전에)

1. **브랜치 확인.** `git status`가 깨끗한지, 현재 브랜치가 `main`이 아닌지 확인한다.
   `git log --oneline HEAD..main`에 커밋이 있으면 `git merge main`으로 최신 main을 먼저 합친다.
2. **이미 구현됐는지 확인.** PLAN의 핵심 이름(함수·데이터 값·테스트 이름)을 코드에서 검색한다.
   이미 있으면 **새로 구현하지 않는다.** 검증과 기록만 하고(3·4절), 보고에 그 사실을 먼저 적는다.
3. **읽을 것.**
   - PLAN의 해당 작업 섹션, 그리고 "구현 순서와 검증"과 "범위 제외"
   - 최신 `docs/DEV-RECORD-*.md` 맨 위 "이 환경에서 확인된 제약"
   - `README.md`의 "핵심 설계 결정" 중 이번 작업과 관련된 절
4. **계획을 먼저 보여준다.** 바꿀 파일, 추가할 테스트 이름, 뒤집히는 기존 테스트를 목록으로 적는다.
   plan mode가 아니어도 이 단계는 거친다.

## 2. 구현

- **범위는 지정받은 작업 하나다.** PLAN의 다른 작업과 "범위 제외" 항목은 건드리지 않는다.
- PLAN의 "검증" 항목은 **하나도 빠짐없이 이름 붙은 테스트**로 만든다.
  테스트 이름만 읽어도 어느 검증 항목인지 알 수 있게 짓는다.
- 시드 JSON(`src/data/*.json`)을 고치면 `src/lib/seedRevision.test.ts` 주석의 규칙대로
  `seedRevision`을 올리고 스냅샷 해시를 갱신한다.
- 기존 테스트가 PLAN 때문에 뒤집히면 고치되, 왜 고쳤는지 테스트 이름이나 주석에 남긴다.
- 화면 규칙은 RTL이 없으므로 **순수 함수 + 소스 스캔** 두 층으로 잠근다.
- PLAN이 모순되거나, PLAN에 없는 설계 판단이 필요하면 **추측하지 말고 멈춘다.**
  무엇이 막혔는지 보고하고 사람의 답을 기다린다.

## 3. 검증 (전부 필수)

1. `npm test` 통과
2. `npm run build` 통과
3. **결함 복원 확인.** 새로 만든 테스트·스캔마다:
   - 대상 파일을 `cp`로 백업한다
   - 그 테스트가 막으려는 결함을 일부러 되살린다
   - 해당 테스트가 **실패하는지** 확인한다
   - 백업에서 되돌리고 `cmp`와 `git status`로 원상복구를 확인한다
   - 되살린 결함이 어떤 테스트도 실패시키지 않으면, 그건 테스트의 구멍이다. 테스트를 보강한다.

## 4. 기록

`docs/DEV-RECORD-<PLAN 버전>.md`에 작업 ID 절로 **이어서** 쓴다.
파일이 없으면 새로 만들고, 맨 위에 이전 버전 DEV-RECORD의 "이 환경에서 확인된 제약"을 이어받는다.
이미 있는 제약 목록은 중복하지 않는다. 새로 알게 된 제약은 그 목록 끝에 번호를 붙여 추가한다.

반드시 들어갈 것:
- 범위 표(이번 커밋 해시, 바뀐 파일)와 테스트 수·파일 수. **문서 안의 수치는 서로 일치해야 한다.**
- 테스트 이름 목록과 각각이 대응하는 PLAN 검증 항목
- 결함 복원 확인 결과 표 (되살린 결함 → 실패한 테스트 → 원상복구 확인)
- 과거 기록·판정이 바뀌지 않는다는 확인 (PLAN이 요구하면 별도 절)
- 실행 출력 원문: `npm test` 요약, `npm run build` 요약, `git rev-list --count main..HEAD`
- 하지 않은 것 (화면 확인, 실기기 확인 등)과 실기기 확인 목록
- 리뷰어에게 묻는 것 (PLAN과 다르게 한 것, 판단을 맡긴 것)

## 5. 커밋

- 이 브랜치에만 커밋한다. push, `main` 머지, `package.json` 버전 상향은 하지 않는다.
- 커밋 메시지는 heredoc으로 쓴다: `git commit -F - <<'MSG'`
- 리뷰 반려를 반영할 때는 **새 커밋**을 만든다. `--amend`로 앞 커밋을 덮지 않는다.
  리뷰어가 앞 커밋과의 차이로 수정 내용을 확인하기 때문이다.

## 6. 리뷰에서 반려됐을 때

- "고칠 것" 번호마다 처리하고, 범위는 원래 작업 그대로 유지한다.
- 3절 검증을 다시 전부 돌린다.
- 기록에 "리뷰 반영" 내용을 덧붙이고, 수치(커밋 표·테스트 수)를 다시 맞춘다.

## 7. 최종 보고 (이 형식 그대로)

```
결과: 완료 | 이미 구현됨 | 중단(사람 필요)
검증: npm test <파일 수>/<테스트 수> 통과, npm run build 통과, 결함 복원 <n>건 확인
커밋: <해시> <제목> (바뀐 파일 <n>개)
하지 않은 것: <없으면 "없음">
```

그 아래에 필요한 만큼 자세히 설명해도 된다. 다만 위 네 줄은 항상 맨 위에 둔다.
