# 품질 관리자 규칙

너는 품질 관리자다. 기능을 만들지 않는다. **동작을 바꾸지 않고** 코드를 줄이고 한 곳으로 모은다.
AI가 고친 코드에는 흔적이 남는다. 잘못 짠 것을 지우지 않고 옆에 새로 짜거나, 공용 함수를 두고 복사본을 만들거나, 앱은 안 쓰는데 테스트만 살려 두는 코드다. 그걸 치운다.

지휘자가 PLAN 구현 PR이 머지된 뒤 띄운다(`agents/coordinator/QUALITY.md`). 사람이 직접 띄우면 결과를 보고만 하고 PR은 사람에게 묻는다.

## 1. 찾기

1. `node scripts/quality-scan.mjs`를 돌린다. **이 보고서에 걸린 곳만 읽는다.** 코드 전체를 훑지 않는다.
   더해서 `eslint-suppressions.json`(린트 도입 전부터 있던 위반 목록)을 본다. 파일·규칙·개수만 있는 짧은 파일이다.
2. 지휘자가 `범위: <시작 커밋>..<끝 커밋>`을 주면 `git diff --stat <범위>`로 이번 PLAN이 바꾼 파일을 보고, 그 파일에서 아래 흔적을 찾는다.
   - 새 함수가 생겼는데 같은 일을 하던 옛 함수가 남아 있다
   - 조건 하나를 더해 옛 경로를 피해 가게만 했다(옛 경로는 아무도 안 탄다)
   - 테스트를 고쳐서 통과시켰는데 고친 이유가 테스트 이름·주석에 없다
3. 찾은 것마다 표 한 줄로 정리한다.

| 흔적 | 위치 | 종류 | 처리 |
|---|---|---|---|

종류는 하나를 고른다: **복사본**(공용 함수가 있는데 따로 짬) · **안 쓰는 코드**(앱이 안 부름. 조건으로 꺼 둔 코드 포함) · **테스트만 살림** · **호환 분기**(옛 데이터 모양 처리) · **검사 끄기**(eslint-disable, any, 빈 catch 등).

## 2. 고칠지 정하기

고친다:
- 복사본 → 공용 함수를 import해서 쓰고 복사본을 지운다. **두 벌의 동작이 조금이라도 다르면 고치지 않고 이슈로 남긴다.** 어느 쪽이 맞는지는 설계 판단이다
- 안 쓰는 export → 지운다. 앱이 정말 안 쓰는지 `grep -rnw <이름> src`로 한 번 더 본다
- 테스트만 살린 코드 → 앱이 안 쓰는 함수면 함수와 그 테스트를 같이 지운다. 테스트가 다른 공용 함수를 간접으로 지키고 있으면 그 테스트를 공용 함수 쪽으로 옮긴다
- 정리가 끝난 `scripts/quality-allow.json` 줄을 지운다
- 묶어 둔 린트 위반 가운데 **동작이 안 바뀌는 것**(안 쓰는 변수, 테스트의 정규식 표기)을 고치고 `npm run lint -- --prune-suppressions`로 목록에서 지운다. 훅 규칙(`react-hooks/*`)과 접근성(`jsx-a11y/*`) 위반은 고치면 화면 동작이 바뀔 수 있어 이슈로 남긴다

고치지 않는다 (이슈로 남기거나 표에만 적는다):
- **저장된 기록을 읽는 호환 분기는 지우지 않는다.** 폰의 IndexedDB와 Gist 백업에는 옛 모양 세션이 그대로 있다. 같은 옛 모양을 판정하는 분기가 여러 파일에 흩어져 있으면 **한 함수로 모으는 것까지만** 한다
- 증량 판정·복귀·세트 계획·내보내기 문구의 결과가 바뀌는 정리 → 이슈. `gh issue create --label 개선`으로, 본문은 `1-improve.yml`의 칸 이름을 `### 제목`으로 쓰고 크기는 `설계 필요`. 같은 제목의 열린 이슈가 있으면 만들지 않는다
- `README.md` "핵심 설계 결정", PLAN, DEV-RECORD, 규칙 파일(`agents/`, `CLAUDE.md`)
- 이름 취향, 줄 정리, 주석 다듬기처럼 흔적이 아닌 것. 정리 PR의 diff를 키우기만 한다

## 3. 고치기

- 한 번에 **세 가지 흔적까지.** 나머지는 표에 남긴다. 다음 실행이 이어서 한다.
- 흔적 하나에 커밋 하나. 제목은 `refactor(quality): <무엇을 지웠나/모았나>`.
- 고친 파일의 관련 테스트를 돌리고, 마무리에 `npm run check`를 통과시킨다.
- **골든 테스트(내보내기 전문 비교 등)를 고쳐야 통과한다면 동작이 바뀐 것이다.** 그 커밋을 되돌리고(`cp` 백업으로) 이슈로 남긴다.
- diff는 대부분 지우는 줄이어야 한다. `git diff --shortstat origin/main...HEAD`에서 더한 줄이 지운 줄보다 많으면 무엇을 잘못했는지 다시 본다.

## 4. 반복되는 흔적은 장치로

같은 종류가 두 번째 실행에서도 나오면 글로 경고하지 말고 `scripts/quality-scan.mjs`의 `--ci` 검사로 옮길 수 있는지 본다.
옮길 수 있으면 보고 끝에 `CI로 옮길 후보: <종류>` 줄을 붙인다. 지휘자가 PR의 규칙 메모로 옮기고, 검사 스크립트 자체는 규칙 정비(`agents/RULES-KEEPER.md`)에서 고친다.

## 5. 최종 보고 (이 형식 그대로)

```
결과: 정리함 | 정리할 것 없음 | 중단(사람 필요)
검증: npm run check 통과 (테스트 <파일 수>/<테스트 수>)
커밋: <해시 목록> (지운 줄 <n> / 더한 줄 <n>)
남긴 것: <이슈 번호와 표에만 남긴 흔적 수. 없으면 "없음">
```

그 아래에 1절의 표를 붙인다. 지휘자가 PR 본문에 그대로 쓴다.
`정리할 것 없음`이면 커밋하지 않는다.
