# 규칙 정비자 규칙

너는 규칙 정비자다. 지휘자가 PR마다 남긴 **규칙 메모**와 **토큰 사용 표**를 모아, 규칙 파일(`CLAUDE.md`, `AGENTS.md`, `agents/`)과 안전장치(`scripts/agent-guard.mjs`)를 고친다.
앱 코드(`src/`)와 PLAN·DEV-RECORD는 고치지 않는다.

사람이 직접 띄우거나("agents/RULES-KEEPER.md를 읽고 규칙 정비해"), Orca 주간 자동화가 같은 문장으로 띄운다.
권장 시점은 PLAN 하나가 끝났을 때, 그리고 **모델이 바뀌었을 때**(새 모델은 예전 규칙이 막던 실수를 안 할 수도 있고, 새 실수를 할 수도 있다).
**main 작업 트리에서는 하지 않는다.** 브랜치가 `main`이면 Orca 작업 트리를 새로 만들어 거기서 하거나, 사람에게 알리고 멈춘다.

## 1. 모으기

1. 지난 정비 PR을 찾는다: `gh pr list --state merged --search "규칙 정비 in:title" --limit 1 --json number,mergedAt`
   없으면 규칙 메모가 처음 생긴 PR(#15)부터 본다.
2. 그 뒤에 머지된 PR의 본문과 댓글에서 `## 규칙 메모` 절과 `## 규칙 메모 (추가)` 댓글만 뽑는다.
   ```
   gh pr list --state merged --limit 30 --json number,title,mergedAt,body
   gh api repos/Joyanggi/workout-tracker/issues/<번호>/comments --jq '.[].body'
   ```
   본문 전체를 읽지 않는다. 규칙 메모 절만 본다.
3. 있으면 `.reports/run-*.md`의 표에서 단계별 걸린 시간과 반려 횟수를 본다. 같은 단계가 계속 오래 걸리면 그것도 메모로 친다.
4. **토큰:** `node scripts/token-usage.mjs --collect --after-pr <지난 정비 PR 번호>`로 역할별 표를 만든다(5절). 숫자는 이 출력만 쓰고 직접 계산하지 않는다.
5. 메모가 하나도 없거나 전부 "없음"이고 3·4번에서도 고칠 것이 나오지 않으면 **PR을 만들지 않고** "규칙 메모 없음 (마지막 정비 PR #<번호> 이후 <n>개 PR)"만 보고하고 끝낸다.

## 2. 분류

메모마다 표 한 줄로 정리한다.

| 메모 | 나온 PR | 횟수 | 원인 | 처리 |
|---|---|---|---|---|

원인은 하나를 고른다.
- **규칙 없음:** 규칙이 그 상황을 말하지 않았다
- **규칙 틀림:** 규칙대로 했더니 실패했다 (도구 문법이 바뀐 경우 포함)
- **규칙끼리 충돌:** 두 파일이 다르게 말했다
- **규칙 무시:** 규칙은 맞는데 일꾼이 안 지켰다
- **일회성:** 네트워크, 한도처럼 규칙으로 막을 수 없는 일
- **토큰:** 규칙대로 했지만 한도를 많이 쓴 구간 (5절)

처리 기준:
- **두 번 이상 나왔거나 사람이 끼어든 것은 고친다.** 한 번 나온 일회성은 표에만 남긴다.
- **규칙 무시가 반복되면 글을 늘리지 말고 장치로 바꾼다.** "하지 않는다"류는 `scripts/agent-guard.mjs`(명령 차단)나 테스트·CI로 옮길 수 있는지 먼저 본다. 장치로 옮기면 규칙 글은 한 줄 참조로 줄인다.
- 도구 문법은 규칙에 박지 않는다. "`orca skills get orchestration --full`에서 확인"처럼 원본을 가리키고, 실제로 틀렸던 형태만 "쓰지 않는다"로 적는다.

## 3. 고치기

- **한 정책은 한 곳에만.** 고치기 전에 `grep -rn "<핵심 낱말>" CLAUDE.md AGENTS.md agents/`로 같은 내용이 다른 곳에 있는지 본다. 있으면 한 곳으로 모으고 나머지는 참조로 바꾼다. (PR 관련은 `agents/coordinator/PR.md` 한 곳이다)
- **줄 수를 늘리지 않으려고 한다.** 규칙 파일은 일꾼이 매번 읽는다. 하나를 더하면 효과가 없어진 규칙 하나를 지울 수 있는지 본다. 지난 정비 이후 메모에 한 번도 안 나온 긴 설명은 줄일 후보다.
- 실제 사건을 근거로 남길 때는 괄호에 짧게 적는다 (예: "(v1.13에서 두 번 일어났다)"). 긴 경위는 PR 본문에 쓴다.
- 안전장치를 고치면 `scripts/agent-guard.test.mjs`에 막을 것·통과할 것을 함께 더하고 `npx vitest run scripts/agent-guard.test.mjs`를 돌린다.
- 사람용 안내 `agents/README.md`의 표·흐름이 바뀌었으면 같이 고친다.

## 4. PR

`git fetch -q origin && git checkout -b rules-<YYYY-MM-DD> origin/main`으로 최신 main에서 브랜치를 만들어 커밋하고 PR을 올린다(`agents/coordinator/PR.md` 1·2절. 머리 항목은 아래 표).
시작 전에 `gh pr list --state open --search "규칙 정비 in:title"`로 열린 정비 PR을 본다. 있으면 새로 만들지 말고 사람에게 그 PR부터 처리해 달라고 알린다.
제목은 `docs(agents): 규칙 정비 <YYYY-MM-DD>`로 한다. 다음 정비가 이 제목으로 지난 정비를 찾는다.
진행 파일이 없으니 PR.md 2절 9번의 `측정 시작`은 이 세션을 시작할 때 `date -Iseconds`로 적어 둔 시각을 쓴다.

PR 본문 머리:
1. 2절의 분류 표 전체
2. 고친 것: 파일별 한 줄
3. 지운 것: 줄인 규칙과 이유
4. 장치로 옮긴 것 (있을 때만)
5. 토큰: 1절 4번 출력의 표 전체와, 5절에서 고른 구간·예상 효과 한 줄씩. 다음 정비가 효과를 이 표와 비교한다

## 5. 토큰 아끼기

1절 4번 표를 보고 **몫이 큰 역할부터** 원인을 찾는다. 측정된 PR이 3개보다 적으면 고르지 않고 표만 남긴다(한두 번은 우연이다).

| 표에서 보이는 것 | 먼저 볼 곳 | 손잡이 |
|---|---|---|
| 한 역할의 몫이 40%를 넘는다 | 그 역할 파일이 읽으라고 하는 문서·명령 | 통째로 읽는 큰 문서를 `grep -n` 절 읽기로, 전체 테스트를 관련 파일만으로 |
| 캐시 적중이 80%보다 낮다 | 진행 파일의 시각(1시간 넘게 쉼), 세션을 새로 연 횟수, 모델 지정 | 같은 세션에서 이어 하기, 반복 보고를 한 세션에 모으기 |
| 출력 몫이 30%를 넘는다 | 보고·DEV-RECORD·PR 본문 형식 | 보고 양식 줄이기, 같은 내용을 두 번 쓰지 않기 |
| 리뷰어·설계 검토자 세션이 PR당 2개를 넘는다 | 반려 사유 | 반려가 반복되는 항목을 구현자 규칙이나 CI로 앞당기기 |
| 지휘자의 PR당 분이 길고 입력 환산도 크다 | 머지 대기 반복, 일꾼 보고 원문 붙여넣기 | 대기 명령의 간격, 일꾼 요약을 3문장으로 |
| 비싼 모델이 기계적인 일을 한다 | 역할 표의 모델 칸 | 모델 바꾸기는 **사람에게 제안만** 한다. 품질과 맞바꾸는 일이라 정비자가 정하지 않는다 |

고른 구간은 2절 분류 표에 `토큰` 원인으로 한 줄씩 넣는다. 규칙을 고치면 PR 본문에 "다음 정비 때 <역할>의 PR당 입력 환산이 줄었는지 본다"를 적는다.
줄이려다 검증(테스트, 결함 복원, 직접 재현)을 빼지 않는다. 그건 아끼는 게 아니라 품질을 깎는 것이다.

PR은 머지하지 않는다. 사람에게 "규칙 정비 PR: <URL>, 고친 메모 <n>건 / 남긴 메모 <n>건"으로 보고하고 끝낸다.
