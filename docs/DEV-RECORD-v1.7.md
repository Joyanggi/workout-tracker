> 7건 전부 구현·배포 완료. **774 테스트 / 43파일** (v1.6의 725에서 +49).
> 라운드 인바리언트(점수·판정·데이터 형식 불변, 소급 효과 없음) 확인 — §7.

## 이 환경에서 확인된 제약 (누적 — 매 라운드 맨 위에 둔다)

1. `npx tsc --noEmit`은 `src`를 검사하지 않는다 → **`npm run build`로 타입 확인**.
2. 개발 브라우저 창은 `visibilityState`가 항상 `hidden`이다 → 소리·rAF·focus 이벤트가
   발화하지 않고, 250ms 인터벌은 ~1Hz로 스로틀된다.
3. vitest에서 `.css`를 `?raw`로 읽으면 **빈 문자열**이 온다 → CSS 값은 소스 스캔으로
   검증할 수 없다. 색·크기는 브라우저 `getComputedStyle` 실측으로 확인한다.
4. `computer` 클릭은 pane이 hidden이면 타임아웃된다 → 조작은 `javascript_tool`로 한다.
5. 이 프로젝트에 React 렌더 테스트(RTL)가 없다 → 화면 규칙은 **순수 함수 + 소스 스캔**
   2층으로 잠근다 (v1.6 §6-14).
6. **`javascript_tool`로는 React 이벤트 일부를 재현할 수 없다** (이 라운드에서 확인, §5):
   - `.click()`은 `onPointerDown/Up` 핸들러를 발화시키지 않는다 (NumberStepper의 ±).
   - `dispatchEvent(new Event('blur'))`도 `input.blur()`도 React의 `onBlur` 커밋을
     일으키지 못했다 → 값이 로컬 `text` 상태에만 남는다.
   - 해결: `PointerEvent('pointerdown'/'pointerup')`를 실제로 디스패치하면 커밋된다.

### 2.1 BB7의 서술이 실제와 달랐다 — 그런데 더 나쁜 결함이 있었다

**틀린 것 세 가지:**

1. **툴팁은 이미 다크였다.** `TOOLTIP_STYLE`이 `background: C.surface` + `--line` 테두리 +
   12px로 이미 정의돼 있었다. "밝은 배경"이 아니다.
2. **활성점도 이미 r=5였다** (`activeDot={{ r: 5 }}`). 계획서의 기준 "r≥5"를 충족한다.
3. **차트는 2개다.** 계획서가 4개(A그룹 추이·감각 점수·주간 수행·종목 히스토리)를 들었지만
   — 감각 점수는 recharts가 아니라 `<div>` 점이고(`.sdots`), **종목 히스토리에는 차트가
   아예 없다.** `ExerciseHistoryScreen` 주석이 그 이유를 적어 두고 있다:
   "차트는 분석 탭(§5.4)이 담당한다. 여기는 원본 숫자를 그대로 보여준다."

**대신 실측으로 두 개의 진짜 결함을 찾았다.** 둘 다 "색을 지정했다고 믿고 있었던" 부류다:

| # | 결함 | 실측 |
|---|---|---|
| ① | hex 사본이 G6 가독성 패스를 따라가지 않았다 | 차트의 `faint: '#64646f'` = **G6가 미달로 교체한 값**. 대비 3.09:1 |
| ② | 축 라벨을 `stroke`로 칠하고 있었다 | SVG `<text>`는 `fill`로 칠해진다. `stroke`는 글자 **윤곽선**이다 → 색이 한 번도 적용된 적 없고 recharts 기본색이 그려졌다. 실측 `rgb(102, 102, 102)` = #666666, 대비 **3.3:1** |

②가 ①보다 심각하다. ①은 "낡은 값을 쓴다"인데 ②는 **"지정이 아무 효과가 없다"**이고,
①만 고쳤다면 여전히 #666666이 그려졌을 것이다 — 사본을 토큰으로 바꾼 뒤에도 화면은
그대로였을 것이고, 나는 고쳤다고 믿었을 것이다. `fill`로 바꾼 뒤 실측 `rgb(140, 140, 152)`,
대비 **5.43:1** (앱 나머지와 같은 기준).

> **계획서가 틀린 것을 지목했지만 그 자리를 파게 만들었다.** BB7의 값은 "툴팁이 밝다"가
> 아니라 "차트를 실측해 봐라"였고, 그것이 정확히 이 라운드에서 가장 큰 수확이었다.

## 3. 구현 중 새로 발견한 것 (3건)

### 3.1 톱니 아이콘이 22px에서 해(sun)로 읽혔다

첫 구현은 "원(r=3.4) + 6방향 짧은 이"였다. 톱니 폴리곤을 그대로 그리면 이 크기에서 이가
뭉치기 때문에 단순화한 것인데, **스크린샷을 찍어 보니 태양이었다.**

차이는 **이가 몸통에 붙어 있는지**다. 해의 빛살은 원과 떨어져 있고, 톱니는 붙어 있다.
그래서 구조를 바꿨다: 몸통 링(r=7) + 축 구멍(r=2.6) + 링에서 밖으로 나가는 이.
톱니바퀴의 세 요소가 다 있으면 6개만으로도 톱니로 읽힌다.

**교훈**: 아이콘은 "무엇을 그렸는가"가 아니라 "무엇으로 읽히는가"로 판정해야 하고,
그 판정은 코드를 보면 알 수 없다. 실제 크기의 스크린샷이 유일한 검증이다.

### 3.2 BB6의 힌트가 기존 결함을 드러냈다 — 화면 숫자와 DB가 어긋났다

워밍업 겹침(BB2-3)을 실측하다 이 상태를 만났다:

| | 화면 | DB |
|---|---|---|
| W (워밍업) | 무게 **40** · "무게 미입력" 경고 | `weight: 0` |
| 1 | 2.5 | `weight: 2.5` |

**힌트가 사실이고 화면 숫자가 거짓이었다.** 원인은 `ExerciseCard`가 스스로 적어 둔 위험이다:

```
key={i}는 **세트를 끝에서만 제거**하는 현재 UI에서만 안전하다.
중간 제거를 추가하면 NumberStepper의 편집 중 로컬 상태가 옆 세트로 옮겨 붙는다.
```

그런데 **주석의 안전 논거가 이미 거짓이다**: `applyAddSet(opts.warmup)`은
`[set, ...entry.sets]`로 **앞에 삽입한다.** 중간 제거를 기다릴 필요가 없고, 워밍업 추가가
이미 모든 인덱스를 밀어낸다. `key={i}`가 붙은 NumberStepper의 로컬 `text` 상태가
인덱스 0에 그대로 남아, 새로 들어온 워밍업 행의 숫자로 보이게 된다.

**재현 조건과 실사용 가능성** (과장하지 않기 위해 명시):
- 필요한 것은 **커밋되지 않은 편집 상태**(로컬 `text`가 살아 있는 상태)에서 워밍업 추가다.
- 실기기에서는 워밍업 버튼을 탭하는 순간 입력이 blur되어 커밋되므로 `text`가 null이 되고,
  그러면 재현되지 않는다. 내가 만든 상태는 **`javascript_tool`이 React의 `onBlur`를
  발화시키지 못해서** 생긴 것이다 (누적 제약 6).
- 즉 **이 창에서는 재현되지만 실기기에서 재현되는지는 확인할 수 없었다.** 그래서 고치지
  않았다 — 고치는 비용이 `SetRecord`에 id 추가 + 백업 스키마 검토이고(주석이 지목한 그것),
  마감 라운드의 범위가 아니다. §8.1·§9로 올린다.

**그럼에도 이것이 BB6의 값이다**: 힌트가 없었으면 화면과 데이터가 어긋난 상태를
**아무도 볼 방법이 없었다.**

### 3.3 vite가 JSON import에 경고를 냈다 (BB5 부작용)

`import pkg from './package.json'`을 넣자 매 테스트 실행마다 경고가 붙었다:
"JSON import without import attributes ... Add `with { type: 'json' }`".
`with { type: 'json' }`으로 고쳐 경고를 없앴다. **테스트 출력의 노이즈는 다음 라운드에서
진짜 경고를 못 보게 만든다** — 이 프로젝트가 `@types/node`를 안 갖고 있어서
`readFileSync` 경로는 쓸 수 없었고, import attribute가 유일하게 깨끗한 길이었다.

## 4. 계획서와 다르게 판단한 것 (4건)

### 4.1 [BB3] 렌치 대신 슬라이더를 그렸다

계획서는 "🔧⚖ 대체 2개 추가"였다. ⚖는 천칭으로 그렸고, 🔧는 **슬라이더**로 그렸다.

- 이 행이 기록하는 것은 "시트 3칸, 등받이 2" 같은 **머신의 조절 위치**다. 슬라이더가
  그것을 그대로 그린다.
- 렌치는 22px·1.8 굵기에서 사선 손잡이와 열린 턱이 뭉쳐 "무언가 도구"로만 읽힌다
  (§3.1에서 톱니로 배운 것과 같은 문제). 그려 보고 판단했다.

### 4.2 [BB5] 계획서의 소스 스캔 규칙을 그대로 쓰지 않았다

계획서: "SettingsScreen에 `/v\d+\.\d+/` 리터럴이 없다."
**그러면 안 된다** — 같은 화면 본문에 "v2.4 규칙"(루틴 문서 버전)이 있다. 앱 버전과 루틴
버전은 다른 축이고, 루틴 버전은 문서를 가리키는 고유명사라 리터럴이 맞다.
그래서 **버전을 표시하는 그 한 줄만** 검사하고, "v2.4 규칙이 그대로 있다"를 함께 잠갔다.

> 처음에 계획서 그대로 썼다가 이 테스트가 실패했다. 실패가 알려 준 것이고, 그래서
> **넓은 금지 규칙은 자기가 무엇을 금지하는지 모른다**는 것을 다시 확인했다.

### 4.3 [BB7] 감각 점수 점의 `title`은 손대지 않고 보고만 한다

`.sdot`이 값을 `title` 속성으로 보여준다. **`title`은 터치에서 절대 뜨지 않는다**
(iOS에 hover가 없다). BB7의 목표가 "터치 시 툴팁이 읽히는지"이므로 이건 정확히 그 문제다.

그런데 고치려면 **탭해서 값을 펼치는 새 조작**이 필요하고, 계획서가 이 라운드의 범위에서
명시적으로 뺀 것이 그것이다 ("새 조작은 다음 실사용 피드백에서"). 그래서 조작을 만들지
않고, 값을 읽을 수 있는 경로만 `role="img"` + `aria-label`로 남겼다 (VoiceOver).
§8.2·§9로 올린다.

### 4.4 [BB7] 툴팁 배경을 `--surface`가 아니라 `--surface-2`로 했다

툴팁은 카드(`--surface`) **위에** 뜬다. 같은 색이면 경계가 테두리 1px에만 의존한다.
한 단 밝은 면이 그 위에 떠 있다는 것을 색이 말하게 했다 (실측 `rgb(31,31,38)` vs
카드 `rgb(22,22,26)`).

### 이 라운드에 의식적으로 한 것

17. **"검사가 실제로 무엇을 잡는지"를 검사한다.** 이모지 정규식과 버전 리터럴 정규식에
    자기검증 케이스를 붙였다 (`EMOJI.test('🔥') === true`, `EMOJI.test('… ▾') === false`).
    부정 단정(`not.toMatch`)은 정규식이 헛돌면 **항상 통과**하므로, 그 정규식이 살아

## 8. 내가 스스로 의심하는 것 (리뷰 핵심)

### 8.1 [중간] `key={i}`의 안전 논거가 이미 거짓이다 (§3.2)

`ExerciseCard`의 주석은 "끝에서만 제거하므로 안전"이라고 적어 두었지만, **워밍업 추가가
이미 앞쪽 삽입**이라 모든 인덱스가 밀린다. 이 창에서는 화면 숫자와 DB가 어긋난 상태를
실제로 만들었다 (화면 40 / DB 0).

- **고치지 않은 이유**: 실기기에서는 blur 커밋이 먼저 일어나 재현되지 않을 가능성이 크고
  (§3.2), 제대로 고치려면 `SetRecord`에 id를 추가해야 한다 — persist되는 타입이라 백업
  스키마까지 함께 봐야 하고, 그건 마감 라운드가 아니라 별도 항목이다.
- **지금 할 수 있는 최소 조치**는 주석의 거짓 논거를 고치는 것인데, 그것만 하면 "위험을
  알면서 두었다"가 되어 다음 라운드가 반드시 봐야 한다.
- **묻는 것**: ① 다음 라운드 항목으로 올릴지, ② 워밍업 추가를 뒤쪽 삽입으로 바꿔
  (세트 번호만 W로) 인덱스 이동을 없앨지 — ②는 "실제 수행 순서가 그렇다"는 현재 근거를
  뒤집는 것이라 판단이 필요하다.

### 8.2 [낮음] 감각 점수 점은 터치에서 값을 읽을 수 없다 (§4.3)

`title`은 iOS에서 뜨지 않는다. `aria-label`을 붙였지만 VoiceOver를 쓰지 않는 사용자에게는
여전히 읽을 방법이 없다. 최신 값은 칩으로 보이므로 **구간별 값만** 닫혀 있다.

새 조작을 만드는 것이 이 라운드 범위 밖이라 보고만 한다. **묻는 것**: 다음 라운드에서
탭 전개를 넣을지, 아니면 구간이 4주 단위라 최신 칩만으로 충분한지.

### 8.3 [낮음] BB4의 접기가 "읽지 않은 알림"을 만든다

첫 배너만 펼치므로, 2번째 이하 배너는 **탭을 하나 더 해야** 보인다. dismiss와 달리
접힘은 저장하지 않으므로 매번 접힌 상태로 시작한다.

- 우선순위가 이미 중요도 순이고, 접히는 것은 백업·보상작용·증량처럼 **오늘 당장의 판단을
  바꾸지 않는** 것들이다. 복귀·디로드는 항상 1번이라 접히지 않는다.
- 다만 "백업 안 됨"이 다른 배너에 밀려 접히는 조합이 존재한다 (복귀 중 + 백업 필요).
  데이터 유실 축이라 storageAtRisk처럼 큐 밖으로 뺄 근거도 있다.
- **묻는 것**: 백업 리마인드를 큐 밖(항상 표시)으로 올릴지. 지금은 계획서의 우선순위
  ("복귀 > 디로드 > 백업")를 그대로 따랐다.

### 8.4 [낮음] `chartTheme()`이 렌더마다 `getComputedStyle`을 8회 부른다

캐시하지 않았다 — 캐시가 **세 번째 사본**이 되는 것을 피하려는 판단이다.
차트 하나 그리는 비용에 비해 무의미한 크기지만, 모듈 스코프에서 한 번 부르므로
(`const C = chartTheme()`) 실제로는 **import당 1회**다. 다크 테마 고정이라 값이 바뀔
일이 없어서 이 구조가 맞다고 봤지만, 라이트 테마가 언젠가 들어오면 이 자리가 바뀐다.

## 9. 리뷰어에게 묻는 것

1. **§8.1** — `key={i}` + 워밍업 앞쪽 삽입. 다음 라운드 항목으로 올릴지, 삽입 위치를

   근거로 다른 것을 그렸다.
4. **§2.1** — BB7처럼 **계획서의 증상 서술이 틀렸지만 그 자리에 다른 결함이 있는** 경우,
   지금처럼 "틀린 것을 명시하고 찾은 것을 고친다"가 맞나. 아니면 서술이 틀린 시점에
   되물어야 하나 (이번엔 되묻지 않고 실측으로 진행했다).
