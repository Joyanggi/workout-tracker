## Z1. 소리 크기 — 볼륨 설정 + 미리 듣기

**피드백**: "노래 들으면서 쓰니 들리긴 하는데 좀 더 적극적이면 좋겠다. 키우거나,
설정에서 소리를 바꿀 수 있게."

**확인된 현재 동작**: 모든 소리가 `beep.tone()`을 지난다 (W2에서 만든 초크포인트).
게인은 TICK 0.2 / CHIME 0.26 / LAST_CYCLE 0.22 / 템포 페이즈 톤 0.14~0.18.
설정에 소리 관련 항목은 없다.

**설계**:

1. `beep.ts`에 모듈 수준 배율 하나를 둔다:
   ```ts
   let volumeScale = 1
   export function setVolumeScale(scale: number): void
   ```
   `tone()`에서 `Math.min(1, gain * volumeScale)`로 적용한다. **모든 소리가 tone()을
   지나므로 이 한 곳이면 틱·차임·마지막 큐·템포 페이즈 톤이 전부 같이 커진다** —
   소리별로 배율을 따로 저장하지 않는다 (틱만 커지고 차임이 안 커지는 갈라짐 금지).
2. 설정: `soundVolume: 'normal' | 'loud' | 'max'` (배율 1.0 / 1.4 / 1.8).
   **기본값 `loud`** — "지금도 들리는데 더 적극적이면 좋겠다"가 피드백이므로 기본
   경험을 올린다. 배율 상한 1.8인 이유: CHIME 0.26×1.8=0.47, 인접 톤 램프 겹침을
   더해도 피크가 1.0을 넘지 않는다 (사인파라 클리핑 전까지는 왜곡 없음).
3. 설정 화면에 세그먼트 + **"미리 듣기" 버튼** (탭이 제스처이므로 `unlockAudio()` 후
   틱 3회 → 차임 재생). 헬스장에서 음악 틀어둔 채로 바로 고를 수 있어야 한다 —
   휴식 타이머가 끝나기를 기다려 확인하는 구조면 설정을 고치는 데 세트 하나가 든다.
4. 부팅 시(`settings.load`)와 변경 시 `setVolumeScale()` 호출.

**하지 않는 것**: 소리 **종류** 선택(음색 프리셋). W2에서 지금 규격(주파수·길이·형태)을
잡는 데 음향 분석 한 라운드가 들었다 — 프리셋마다 그 검증을 반복해야 하고, X10의
"유지 대상을 늘리지 않는다"에 반한다. 피드백의 목적(더 적극적으로 들리게)은 볼륨으로 달성된다.

**테스트**: 배율 적용·클램프(≤1) 단위 테스트. `audioIndependence` 소스 스캔이 새 export를
막지 않는지 확인.

## Z2. 템포 가이드 수동 종료 → 자동 종료와 같은 체인 (기록 + 세트 체크 + 휴식 시작)

**피드백**: "도중에 종료하면 그때까지 회수가 입력되는 건 좋은데 휴식이 자동으로 안 돌아간다.
의도한 건가? 수행이 안 돼서 멈출 수도, 화장실 때문일 수도 있어서?"

**확인된 현재 동작**: 의도된 비대칭이 맞다. 자동 종료(`onComplete`)는 기록→체크→휴식까지
가고, 수동 종료(`onDone`)는 반복수만 적는다 (ExerciseCard 523~526행). 수동 값이 추정치라
사용자 확인(체크)을 남겨둔 설계였다.

**설계 — 비대칭을 없앤다. 수동 종료도 기록 + 체크 + 휴식 시작.**

근거: 수동 종료의 **대다수 사례가 "세트가 거기서 끝났다"다.** 루틴 문서 13장이 말하는
세트 종료 신호가 바로 "리듬을 못 따라가기 시작하는 순간"이고, 시트 하단 안내문도 그때
먼저 종료하라고 한다 — 즉 수동 종료는 예외 경로가 아니라 **설계된 정상 종료 경로**다.
정상 경로가 자동 경로보다 탭이 2회 많을(체크 + 휴식 확인) 이유가 없다.

화장실 같은 진짜 중단은 드문 쪽이고, 잘못 시작된 휴식 타이머는 탭 1회로 끄면 되고
체크는 탭 1회로 풀면 된다 — **실패의 방향이 현상 유지다** (X5 원칙): 잘못돼도 되돌리기가
한 탭이고, 기록이 손상되지 않는다.

구현: ExerciseCard의 `onDone`을 `onComplete`와 동일 체인으로 (reps > 0일 때
patchSet → 미체크면 onCheck). 카운트인 중 취소(reps 0)는 지금처럼 아무것도 하지 않는다.
버튼 라벨을 `종료 — 약 N회 기록 · 휴식 시작`으로 바꿔 무슨 일이 일어나는지 말해준다.
"약" 라벨과 그 근거 주석(V1)은 유지한다 — 값의 신뢰도 구분은 여전히 유효하다.

**테스트**: 수동 종료 경로가 체크·휴식까지 가는지, 0회 취소가 기록을 건드리지 않는지.

## Z3. 세트 간 휴식 기록·차등 — 기각 (내보내기에 파생 간격만 추가)

**피드백**: "세트 사이 휴식도 기록에 포함되나? 점진적 과부하에 휴식시간도 영향이 있고,
세트 간·운동 간 휴식이 운동학적으로 달라야 하면 적용되면 좋겠다. **과하거나 효과가
미미하면 수정 안 해도 돼.**"

**판정: 위임 조건에 해당한다 — 기능은 만들지 않는다.** 근거 세 가지:

1. **휴식 단축은 이 프로그램의 과부하 축이 아니다.** 비대 목적에서 세트 간 2~3분이
   1분보다 우위라는 것이 현재 근거의 합의다 (짧은 휴식은 다음 세트의 반복수를 깎아
   세션 볼륨 자체를 줄인다). 휴식을 줄여가는 밀도(density) 조작은 컨디셔닝 기법이지,
   v2.4가 정의한 과부하(더블 프로그레션: 반복 → 무게)와 경쟁시킬 변수가 아니다.
   기록해서 줄이도록 유도하면 오히려 프로그램을 해친다.
2. **종목별 차등은 이미 있다.** v2.4 문서가 종목마다 `restSec`을 규정하고 앱이 그대로
   쓴다 (A그룹 길게, B그룹 짧게). "세트 간 vs 운동 간"의 남는 차이는 다음 종목으로
   이동·세팅하는 시간인데, 이것은 통제할 훈련 변수가 아니라 그냥 헬스장 동선이다.
   현재도 마지막 세트 체크 후 타이머가 그 종목 restSec으로 돌고, 그 시간이 자연스럽게
   전환 시간을 겸한다 — 현행 유지.
3. **데이터는 이미 있다.** 세트마다 `doneAt` 타임스탬프가 저장된다. 별도 입력 UI 없이
   전부 파생 가능하다.

**남기는 것 하나**: MD 내보내기의 세트 줄에 **직전 세트와의 간격(분:초)**을 파생해 추가한다
(같은 종목 내에서만, 첫 세트는 생략). 캡션에 "간격 = 앞 세트 체크 ~ 이 세트 체크,
수행 시간 포함"을 명시한다 — 순수 휴식이 아니라는 것을 LLM이 알아야 해석이 안 망가진다.
이걸로 월간 분석 때 "휴식이 점점 길어지는 드리프트" 같은 패턴은 잡을 수 있다.
앱 화면에는 아무것도 추가하지 않는다.

## Z4. 식사 알림 — .ics 캘린더 내보내기

**피드백**: "원하는 슬롯에 알림을 켜두면 그 시간에 알려주는 것. 오후·보충 블록은 까먹는다."

**플랫폼 사실 (T6 조사와 같은 계열)**: iOS PWA에서 **앱이 스스로 예약 알림을 울릴 방법은
없다.** 로컬 예약 알림 API(Notification Triggers)는 폐기됐고, Web Push는 서버가 매일
정시에 푸시를 쏴줘야 한다 — 서버 없는 것이 이 프로젝트의 전제이므로 기각.
앱 안에 "알림 켜기" 토글을 만들면 **켜져 있는데 안 울리는 거짓 UI**가 된다. 만들지 않는다.

**설계 — 알림은 iOS 캘린더에 위임하고, 앱은 그 일정을 만들어준다:**

1. 식단 탭에 "식사 알림 내보내기" 진입점. 슬롯 선택 UI — **기본 선택은 잊기 쉬운
   슬롯만** (오후 간식·보충 블록. 아침·점심·저녁은 기본 해제 — 피드백 그대로).
2. 선택된 슬롯마다 `timeHint` 시각의 **매일 반복 VEVENT** (`RRULE:FREQ=DAILY`) +
   `VALARM` (TRIGGER 정시)을 만든 .ics를 `share.ts`(기존 공유 경로)로 내보낸다.
   제목은 슬롯 이름 + 품목 요약 (예: "보충 블록 — 쉐이크·바나나").
3. UID는 슬롯 id 기반으로 고정한다. 다만 iOS 가져오기는 갱신이 아니라 중복 생성될 수
   있으므로, 안내 문구에 "시간을 바꿔 다시 내보냈다면 캘린더에서 기존 알림을 지우고
   추가하세요"를 명시한다.
4. 훈련일 전용 슬롯(훈련 전·직후)은 요일이 유동이라 기본 해제로 두되 선택은 허용하고,
   선택 시 "휴식일에도 울립니다" 캡션을 붙인다.
5. 안내 문구에 한계를 정직하게: "앱이 직접 알림을 보낼 수는 없습니다 (iOS 웹앱 제약).
   대신 아이폰 캘린더가 울립니다."

**테스트**: ics 생성 순수 함수 (RRULE·VALARM·이스케이프·UID 고정성). 홈 상단 "다음 식단"
표시는 그대로 둔다 — 이 기능과 역할이 다르다 (보고 있을 때 vs 안 보고 있을 때).

## Z5. 세션 중 다른 탭 접근 — 세션 최소화

**피드백**: "운동 시작하면 다른 탭에 접근이 안 된다. 보고 싶으면 세션을 버리거나 강제로
기록할 수밖에 없다."

**확인된 현재 동작**: `view === 'session'`이면 App이 SessionScreen만 렌더한다 (§5.2
"전체화면 입력" — 의도였지만, 나가는 문이 종료/버리기뿐인 것은 의도가 아니라 누락이다).
세션 상태는 store + Dexie에 있어 재부팅 복구도 이미 되므로, **화면을 떠나는 것 자체는
데이터에 아무 위험이 없다.** 홈에는 이미 "진행 중: {Day} · 이어서" 배너가 있다 (217행).

**설계**:

1. SessionScreen 헤더에 **뒤로(최소화) 버튼** — `setView('tabs')`. 세션은 그대로 열려 있다.
   종료·버리기와 시각적으로 구분한다 (파괴적 동작이 아니다).
2. `view === 'tabs'`이고 열린 세션이 있으면 **TabBar 바로 위에 재개 스트립**:
   "🏋️ D2 진행 중 · 32분 — 이어서". 어느 탭에 있든 보인다. 휴식 타이머가 돌고 있으면
   남은 초를 같이 보여준다 ("휴식 0:42"). 홈의 기존 배너와 역할이 겹치면 홈 배너를
   스트립으로 통합해도 된다 (구현 판단에 맡긴다 — 같은 정보가 두 줄 뜨는 것만 피할 것).
3. **휴식 타이머 소유권을 App으로 올린다 (이 항목의 핵심 함정).**
   지금은 SessionScreen이 `useRestTimer()`를 소유한다 — 탭으로 나가면 훅이 언마운트되어
   **차임·카운트다운 틱이 죽는다.** endTime은 localStorage에 있어 복귀하면 표시는 정확하지만,
   식단 체크하러 나가 있는 동안 휴식이 끝나면 소리가 안 난다 — 이 기능을 만드는 이유
   (운동 중에 다른 탭을 본다)와 정확히 충돌한다.
   App이 단일 인스턴스를 소유하고 SessionScreen과 재개 스트립에 내려준다.
   **인스턴스 두 개 금지** — localStorage는 load 시점에만 읽으므로 라이브 동기화가 안 되고,
   두 개면 알림이 두 번 울리거나 한쪽이 낡는다.
4. 세션 종료·버리기 UI는 지금처럼 세션 화면 안에만 둔다.

**테스트**: 타이머 단일 소유 (App 이하에서 `useRestTimer(` 호출이 정확히 1곳 —
소스 스캔 방식, `audioIndependence`와 같은 수법). 최소화 → 복귀 시 세션·타이머 유지.

## Z6. 식단 수행도 세분화 — 영양 기여 가중 연속 점수 + 슬롯 마크 5단

**피드백**: "오메가3 1캡슐만 안 먹어도 주황색. 상태값 3단계가 아쉽다."

**확인된 현재 동작**: 원인이 두 겹이다.

- **점수가 개수 기반이다**: `baseSlotScore`가 체크 **개수** 비율을 full(1)/partial(0.5)/
  scarce(0.25) 3단으로 양자화한다. 아침에서 오메가3 하나 빼면 2/3 체크 → partial 0.5 —
  **캡슐 하나가 끼니의 절반을 깎는다.** 오메가3 1표 = 현미밥 150g 1표인 것이 근본 문제.
- **표시도 3단이다**: 슬롯 마크 ●◐✗, 날짜 판정 good/mid/poor.

**설계 — 점수를 영양 기여로 가중한 연속값으로, 표시는 5단으로:**

1. `baseSlotScore`의 체크 경로를 연속값으로 바꾼다:
   ```
   weight(item) = max(10, item.kcal + item.proteinG × 4)
   score = Σ(checked weight) / Σ(total weight)
   ```
   - 단백질 ×4 추가 가중: kcal에 이미 포함돼 있지만 한 번 더 얹는다 — 이 프로그램의
     1급 지표가 단백질 160g이므로, 단백질원 누락이 같은 kcal의 탄수 누락보다 무거워야 한다.
   - floor 10: 0kcal에 가까운 보충제(오메가3·비타민)가 가중 0이 되지 않게 한다.
     완전 0이면 체크 여부가 점수에 안 보여 체크할 이유가 사라진다 — "거의 안 깎이지만
     0은 아니다"가 맞는 자리다.
   - 예시 (아침: 현미밥 ~220 + 반숙란 ~140 + 오메가3 ~10 가중): 오메가3만 누락 →
     score ≈ 0.97 → 날짜 판정 good 유지. **피드백 사례가 이 공식으로 직접 해소된다.**
   - 대체(similar/other/cheat)·스킵·추가 상한(G2)·크리티컬 스킵(H3) 매핑은 전부 유지.
     바뀌는 것은 "체크로 채운 슬롯"의 점수뿐이다.
2. 슬롯 마크를 5단으로: `● (=1) / ◕ (≥0.8) / ◐ (≥0.45) / ◔ (>0) / ✗ (0)` + 미기록 ○.
   grade 클래스도 5단으로 나눠 색을 세분화한다 (기존 full/part/zero 3색 → 5색,
   G6에서 실측한 대비 기준 유지).
3. 일 요약에 퍼센트를 노출한다: "준수 ● 92%" — 마크만으로는 0.86과 1.0이 같아 보인다.
4. **날짜 판정(good/mid/poor)과 캘린더 점 3단은 유지한다.** 캘린더는 한눈 판독용이고,
   연속 점수 개선만으로 사용자 사례가 mid→good으로 올라간다. 임계값 0.85/0.5도 유지.

**소급 효과 (관례 — DEV-RECORD에 필수 기재)**: 파생 비저장 원칙에 따라 과거 날짜의
점수·판정이 전부 재계산된다. 방향은 대부분 **상향**이다 (개수 양자화가 소액 항목 누락을
과하게 깎던 것이 풀린다). 하향 가능 사례: 단백질원만 빼고 체크한 슬롯 (예전엔 절반 이상
체크로 partial 0.5, 이제 가중 비율로 그 밑으로 내려갈 수 있음) — 이쪽이 더 정확한 값이다.

**테스트**: 가중 공식 단위 테스트 + **오메가3 시나리오를 이름 붙은 테스트로 고정**
("보충제 하나 누락은 good을 깨지 않는다") + 대체·스킵 경로가 안 바뀌었음을 잠그는 테스트.

## ✅ Z7. 백업 시각 표시 — UTC 노출 + 해시 스킵의 모호한 보고 (리뷰 후속, 2026-08-05 실사용 발견)

> **완료 (2026-08-06).** 테스트 683 → **697**. 네 항목 전부.
>
> **계획서가 지목한 두 곳보다 넓었다**: `slice(0, 16)` 복제가 **네 곳**이었다 —
> 계획서 2곳(GistPanel 27·194) + 내 grep이 찾은 3번째(GistPanel 220, 복원 스테이징) +
> **인바리언트 테스트가 잡은 4번째**(`ImportPanel` 80행, 가져오기 스테이징).
> X3에서 배운 "모으는 것과 지우는 것은 다른 작업"이 또 확인됐다 — 이번에는 기계가 잡았다.
>
> 테스트를 **실행 환경 시간대에 의존하지 않게** 썼다: 오프셋을 직접 계산해 기대값을 만들고,
> "UTC보다 앞선 시간대에서만 성립"하는 비교는 조건으로 감쌌다. 환경을 가정한 테스트가
> 이 프로젝트에서 여러 번 문제였다.
>
> **브라우저 실측** (Asia/Seoul, +540분):
> | 값 | 예전 표시 | 지금 표시 |
> |---|---|---|
> | `2026-08-04T23:56:50Z` (버튼 누른 순간) | 08-04 23:56 | **2026-08-05 08:56** |
> | `2026-08-04T12:52:00Z` (어젯밤 자동 백업) | 08-04 12:52 | **2026-08-04 21:52** |
> | 리마인드 기준일 | 2026-08-04 | **2026-08-05** |
>
> 스킵 문구 실측: **"변경 없음 — 마지막 백업 2026-08-05 08:56"** (외부 요청 0건).
> 인바리언트 2건을 되돌려 확인 (UTC slice 복원 → 2건 실패 / skipped 제거 → 1건 실패).

**증상**: 8월 5일에 "지금 백업"을 눌렀는데 "백업 완료 2026-08-04 12:56"이 떴다.
사용자가 "백업이 된 건데 시간만 오류인지 판단이 안 선다"고 보고 — **판단이 안 서는 것
자체가 결함이다.** 백업 상태 표시의 존재 이유가 그 판단을 대신 해주는 것이다.

**원인 — 표시가 UTC다. 데이터는 무사** (Gist 리비전 이력으로 확정):

> **정정 (2026-08-05).** 첫 진단은 "해시 스킵이 발동해 옛 시각이 보였다"였는데,
> 사용자가 "아침 식단을 등록했는데 왜 건너뛰기냐"고 반박했고 그게 맞았다 — 내용이
> 바뀌었으면 스킵은 발동할 수 없다. Gist 리비전 이력을 직접 조회해 배제했다:
> `23:56:50Z`(= **8/5 08:56 KST**, 버튼 누른 순간) 리비전이 실제로 생성됐고 그 안에
> 8/5 아침 기록이 들어 있다. **업로드는 정상 — 혼란은 전부 UTC 표시가 만들었다.**

1. **표시가 UTC다.** `lastBackupAt`은 GitHub API의 `updated_at`(UTC ISO)이고,
   GistPanel이 `s.at.slice(0, 16).replace('T', ' ')`로 **그대로 자른다** (27행·194행 두 곳).
   사용자가 본 "08-04 12:52"는 **어젯밤 21:52 KST**(저녁 기록 후 자동 백업)이고,
   버튼을 눌러 새로 올라간 시각도 "08-04 23:56"으로 표시된다 — **KST 자정~09시 사이의
   모든 백업은 UTC로 하루 전 날짜가 된다.** 아침에 백업할 때마다 재현되는 창이다.
2. **해시 스킵의 보고 문구도 같은 결함 부류다** (이번 사건의 원인은 아니었지만 잠재).
   스킵이 발동하면 `syncNow`가 `{status:'done', at:lastAt}`을 반환하는데, 화면 문구
   "백업 완료 <옛 시각>"은 방금 업로드한 것과 구분되지 않는다. `lastBackupAt`을
   갱신하지 않는 것 자체는 맞다 (올린 게 없으므로) — 틀린 것은 문구다.

**설계**:

1. `dates.ts`에 `formatDateTimeLocal(iso)` 하나 — UTC ISO를 기기 로컬(KST)
   `YYYY-MM-DD HH:mm`으로. **GistPanel 두 곳이 같은 함수를 쓴다** (지금은 같은 slice
   로직이 두 곳에 복제돼 있다 — 패턴 B, mmss를 뽑은 §8.3과 같은 부류).
2. `SyncState`의 `done`에 `skipped?: boolean`을 추가하고, 스킵 경로는
   **"변경 없음 — 마지막 백업 <로컬 시각>"**으로 표시한다. 업로드 경로는 지금처럼
   "백업 완료 <로컬 시각>". 사용자가 버튼을 눌렀을 때 "올라갔다 / 올릴 게 없었다"가
   문구만으로 갈려야 한다.
3. `backupReminder`의 `lastBackupAt.slice(0, 10)`도 UTC 날짜다 — KST 자정~09시
   사이 업로드는 하루 어긋난다. 같은 로컬 변환을 지나게 한다 (경계 테스트 포함:
   "UTC 15:30 = KST 다음날 00:30 업로드가 오늘로 계산된다").
4. §8.1 판정 반영: `itemWeight`의 ×4 주석에 "선택한 미검증 계수"임을 명시 (한 줄).

**테스트**: 로컬 변환 (UTC→KST 날짜 경계) · 스킵 상태 문구 분기 · GistPanel에 slice
복제가 없다는 소스 잠금.
