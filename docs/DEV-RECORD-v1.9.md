## 이 환경에서 확인된 제약 (누적 — 매 라운드 맨 위에 둔다)

1. `npx tsc --noEmit`은 `src`를 검사하지 않는다 → **`npm run build`로 타입 확인**.
2. 개발 브라우저 창은 `visibilityState`가 항상 `hidden`이다 → 소리가 들리지 않고, rAF·focus
   이벤트가 발화하지 않고, 250ms/80ms 인터벌이 ~1Hz로 스로틀된다.
3. vitest에서 `.css`를 `?raw`로 읽으면 **빈 문자열**이 온다 → 색·크기는 브라우저
   `getComputedStyle` 실측으로 확인한다 (이번 라운드에서 diff 줄 대비 6.28:1을 그렇게 쟀다).
4. `computer` 클릭은 pane이 hidden이면 타임아웃된다 → 조작은 `javascript_tool`로 한다.
   **단 `screenshot`은 hidden에서도 찍힌다** (이번에 ▾ 버튼 판정에 그게 결정적이었다).
5. React 렌더 테스트(RTL)가 없다 → 화면 규칙은 **순수 함수 + 소스 스캔** 2층으로 잠근다.
6. `javascript_tool`로 React 이벤트 일부를 재현할 수 없다: `.click()`은 `onPointerDown/Up`을
   발화시키지 않고(→ `PointerEvent` 디스패치), `blur()`는 포커스 없는 문서에서 이벤트를
   만들지 않는다(→ 버블링 `focusout`). **이번 라운드의 버튼들은 `onClick`이라 `.click()`으로
   충분했다.**
7. 소리는 이 창에서 들을 수 없다 (제약 2) → 오디오는 단위 스펙 + `createOscillator` 후킹.
8. `git checkout <파일>`은 커밋되지 않은 작업을 버린다 → 되돌리기는 `cp` 백업으로 한다
   (v1.9에서도 시드 편집 전에 백업을 먼저 떴다).
9. **새로 확인:** `innerText` 부분 문자열 매칭으로 요소를 고르면 안 된다. `find(c =>
   c.innerText.includes('올리브오일'))`이 **닭다리살 칩**을 잡았다 — 그 칩의 문구가
   "200g · 그날 올리브오일 생략"이기 때문이다. 한 번 잘못된 측정값(kcal 330)을 만들었고
   그건 앱 결함이 아니라 **내 선택자 결함**이었다. 인덱스나 정확 일치로 고른다.

## 3. DD1 — 두 플랜의 차이를 화면이 말한다

`diet.comparePlans(base, other)` + `planDiffText`. 화면 문구:

```
보정 1,500
1,566kcal · 단백질 162g
감량 1,800 대비 저녁: 현미밥 1개 빠짐 · −215kcal · 단백질 −4g
```

(실측 캡처 그대로 — 플랜 시트 행 아래 한 줄)

### 3.1 총량을 품목 델타의 합으로 구하지 않았다

`kcalDelta`는 `planTotals(other) − planTotals(base)`다. 품목 델타를 합쳐도 같은 값이지만
**합계를 두 경로로 계산하면 언젠가 갈린다** (이 프로젝트의 결함 B). 대신 둘이 일치한다는
사실을 테스트가 잠근다 (3개 플랜 쌍에 대해 `items` 합 === `kcalDelta` === `planTotals` 차이).

### 3.2 문구를 화면이 들고 있지 않다

스캔: `DietPlanSheet.tsx`에 `현미밥`·`빠짐`이 없어야 한다. 결함 복원으로 확인했다 —
`planDiffText(base, plan)`를 `'저녁: 현미밥 1개 빠짐'` 리터럴로 바꾸면 테스트가 실패한다.

## 4. DD2 — 매일 같은 5끼

### 4.1 무엇을 지우고 무엇을 남겼나

| 대상 | 처리 | 이유 |

옛 플랜의 이름만 `감량 1,800 (구)`로 바꿨다. **판정이 아니라 표기**이고, 목록에서 사라진

않는다는 판단이지만, 리뷰어가 과거 내보내기 문서의 텍스트 변화를 문제로 본다면 되돌리기는
JSON 한 줄이다 (§9 질의 1).

### 4.2 조용히 망가질 수 있었던 곳 — 기본 플랜 이관

계획서에 없던 결함을 미리 잡았다. `ensureSeed`는 `defaultDietPlanId`를 **없을 때만** 채운다
(사용자 선택을 덮지 않기 위해). 그래서 기존 설치본에서는:

- 플랜 시트는 새 플랜만 보여주는데
- `defaultDietPlanId`는 숨긴 `cut-1800`을 계속 가리켜서
- **오늘 화면이 옛 6끼 구성으로 열린다** — 사용자가 고른 적도 없는 상태로.

`supersededBy`를 데이터에 두고 시드에서 이관한다. **선택을 덮는 것이 아니라 같은 선택을 새
id로 옮기는 것**이므로 "사용자 선택 존중"과 충돌하지 않는다.

실측으로 확인했다 (v1.8 상태를 재현 → 새로고침):

| | 되돌린 값 | 새로고침 후 |

| `defaultDietPlanId` | `cut-1800` | **`cut-1800-u`** |
| `seededDietRevision` | 1 | 2 |
| 과거 DietDay의 `planId` | `cut-1800` | **`cut-1800` (그대로)** |

### 4.3 연속일 경고의 근거를 플래그에서 총량으로

## 5. DD3 — 단백질원 변형

### 5.1 기본 변형을 JSON에 두 번 적지 않았다 (계획서와 다르게 한 것)

계획서: "`variants?: {...}[]` — **첫 변형이 기본**(가슴살)". 그대로 하면 가슴살 2팩의
`kcal: 180`이 품목 필드와 `variants[0]`에 **두 벌** 생긴다. 하나만 고치면 갈라지고, 그게
이 프로젝트가 반복해서 만든 결함 A(손으로 쓴 파생값)의 형태다.

그래서 **JSON에는 대체안만** 적고 `variantsOf(item)`이 0번을 품목 자신에서 합성한다.
API 수준에서는 계획서 문장이 그대로 성립한다 (`variantsOf(item)[0]`이 기본).

부수 효과로 **DD3.4가 공짜가 됐다**: "가중치는 기본 변형 기준으로 고정"은 `itemWeight(item)`이
품목 필드를 쓰는 것만으로 이미 참이다. 손으로 지킬 규칙이 아니라 구조가 된다.

### 5.2 화면과 판정이 갈리는 구멍을 막았다

5-b("마지막 선택을 기억한다")를 넣으면 곧바로 결함 B의 자리가 생긴다:

- 기억된 기본값이 다리살 → 카드에 "닭다리살 200g"이 보인다
- 그런데 기록에는 선택이 없다 → 요약은 **가슴살 kcal**로 계산한다
- 화면과 판정이 다른 말을 한다

처방: `seedVariantChoices` — **기록이 생기는 순간 그때 화면에 보였던 선택을 기록에 새긴다.**
호출은 편집기 `mutate` **한 곳**이다 (op마다 부르면 새 op에서 빠뜨린다). 그래서 기록은 항상
자기 자신으로 완결되고, 나중에 기본값을 바꿔도 지난 날의 마크로가 흔들리지 않는다.

실측: 점심 "전부 먹음" 한 번 → `{ checkedItemIds: [...4개], variantChoices: { "chicken-2": 0 } }`.
0도 명시적으로 쓴다 — 기록이 설정을 참조하지 않아야 한다.

### 5.3 미기록 슬롯에는 기록을 만들지 않는다

`applyVariantChoice`가 없는 기록을 만들면 `{ checkedItemIds: [] }`가 되어 그 슬롯이 **0점으로
판정에 들어간다** — 먹기 전에 "오늘은 다리살" 하고 고른 것이 "안 먹었다"로 집계되는 셈이다.
그 경우 선택은 `settings.variantDefaults`에만 남고, 표시는 그것으로 충분하다.

실측: 점심 기록을 지운 뒤에도 칩은 `☐ 닭다리살 200g · 그날 올리브오일 생략`이고 요약은
`기록 0/5슬롯`이다 (유령 기록 없음). 저녁 칩은 `☐ 닭가슴살 3팩` — 기억은 **슬롯×품목** 단위다.

### 5.4 마크로 정직성 — 실측 수열

| 조작 | 화면 kcal | 근거 |
|---|---|---|
| 점심 전부 먹음 (가슴살) | 510 | 문서 표의 점심 구성 |
| 다리살로 바꿈 (오일 그대로) | **670** | +160 — 어긴 날은 초과가 정직하게 보인다 |
| 올리브오일 체크 해제 | **555** | 510 + 45 = 문서의 "실효 +45kcal" |

단백질은 38 → 36 (−2, 문서와 일치). 목표(분모)는 1,781/166으로 **고정** — 변형은 그날의
선택이고 플랜의 목표량이 아니다.

계획서 DD3.5대로 오일 생략을 **강제하지 않는다.** 앱은 판단하지 않고, 합계가 사실을 보여준다.

### 5.5 문서 로테이션 표와 1:1

| 슬롯 | 앱의 변형 | 문서 |
|---|---|---|
| 점심 | 닭가슴살 2팩 / 닭안심 180g / 닭다리살 200g · 그날 올리브오일 생략 | 3택 그대로 |
| 저녁 | 닭가슴살 3팩 / 닭안심 270g | 2택 (다리살 **없음** — 뺄 지방원이 없다) |

테스트가 잠그는 것: 안심은 단백질 등가 · 다리살은 −2g/+160kcal · 오일 생략 시 +45 ·
저녁에 다리살이 없다 · 변형을 가진 품목이 정확히 그 둘뿐이다.

### 5.6 점수는 변형 간 동등

문서가 셋 다 허용하므로 어느 것을 골라도 감점이 없다. 세 선택 모두 슬롯 점수 1.0 (실측),
`itemWeight`는 `180 + 34×4`로 고정.

## 6. DD4 — 그램 표기

새 플랜에서 채소 `1접시` → **`150g`** (kcal 0 취급 유지), 변형 수량은 180g·200g·270g.
옛 플랜은 `1접시` 그대로 — 과거 기록이 그 문구로 남아 있어야 한다. 테스트가 양쪽을 잠근다.

## 7. 새 스캔·규칙 — 전부 결함 복원으로 실패 확인

관례("새 스캔은 결함을 되돌려 실패를 확인한다")를 8건 전부에 적용했다.

| # | 검사 | 되돌린 결함 | 결과 |
|---|---|---|---|
| 1 | 플랜 시트가 문구를 파생시킨다 | `planDiffText(...)` → 리터럴 | 실패 ✓ |
| 2 | 훈련일 세그먼트가 없다 | `diet-daytype` + `applyTrainingDay` 부활 | 실패 ✓ |
| 3 | mutate가 변형 초크포인트를 지난다 | `seedVariantChoices(...)` 제거 | 실패 ✓ |
| 4 | 화면이 `item.qty`를 직접 읽지 않는다 | `variant.qty` → `item.qty` | 실패 ✓ |
| 5 | 시드가 기본 플랜을 이관한다 | `successorOf(...)` → `undefined` | 실패 ✓ |
| 6 | 과거 판정 불변 | `slotsFor`가 `restDaySlots`를 무시 | 실패 ✓ |
| 7 | 변형 선택 우선순위 (기록 > 기억) | 우선순위 뒤집기 | 실패 ✓ |
| 8 | 마크로 정직성 | 요약이 기본 변형 값을 쓰게 | 실패 ✓ |

자기검증도 함께 넣었다 (스캔 2·4): 금지 형태를 문자열로 주면 정규식이 실제로 잡고, 허용
형태는 안 잡는다는 것을 같은 파일에서 확인한다.

## 8. 화면 판정 — ▾ 하나가 실패했다

품목 옆 변형 버튼을 계획서대로 **"▾"만** 넣었다. 375px 실측 캡처에서 그것은
**빈 칸에 점 하나**로 읽혔다 — 체크박스처럼 보이고 무엇을 하는 버튼인지 알 수 없다.
BB1의 기어 아이콘이 해로 읽혔던 것과 같은 실패다: **아이콘은 그린 것이 아니라 읽히는 것으로
판정한다.** `바꾸기 ▾`로 바꿨고, 375px에서 같은 줄에 그대로 들어간다 (줄바꿈 페널티 없음).

diff 줄 색도 실측에서 한 번 바꿨다. 처음엔 `--accent`(주황)였는데 캡처에서 **선택된 행의 금색
강조와 같은 계열**로 보였다 — 캘린더에서 이미 고친 혼동(색이 "선택"인지 "정보"인지)이라
새 색 의미를 만들지 않고 `--text`(밝기)로 눈에 띄게 했다. 대비 실측 6.28:1 / 13px (AA 통과).

## 9. 리뷰어에게 묻는 것

1. **옛 플랜 이름에 "(구)"를 붙였다** (§4.1). 목록에서 사라진 플랜을 과거 날짜에서 볼 때
   "왜 못 고르나"에 답하려는 것이고 판정은 건드리지 않는다. 다만 **과거 내보내기 문서의
   헤더 텍스트가 바뀐다** (`### 식단 — 감량 1,800 (구) · 훈련일 · …`). LLM 분석 경로의
   과거 문자열 안정성을 더 중요하게 본다면 되돌린다.
2. **연속일 경고 대상을 총량 파생으로 바꿨다** (§4.3). 계획서 범위 밖이지만 DD2가 만든
   결함(옛 감량 플랜에 경고)을 막기 위한 것이다. 범위 초과로 보면 되돌리고 대신
   "옛 플랜은 경고 제외" 조건으로 좁힐 수 있다.
3. **`variantDefaults`를 settings에 뒀다** (계획서 5-b 그대로). 백업 settings 덤프에 실리므로
   기기 교체에 따라간다. `SCHEMA_VERSION`은 올리지 않았다 (키 추가는 하위 호환) — v1.8의
   `variantChoices`와 같은 판단이다. 이견 있으면 알려달라.
4. **다리살 변형의 조건을 수량 문구에 넣었다** (`200g · 그날 올리브오일 생략`). 그래서 칩·
   내보내기·변형 시트가 전부 그 조건을 말한다. 다만 칩 문구가 길어진다(§9-4 캡처) —
   조건을 시트에만 두는 안도 있다.

## 10. 실기기 확인 목록

식단은 소리가 없어서 이 창에서 대부분 확인됐다. 실기기에서만 확인 가능한 것:

1. **기존 설치본 업데이트** — 앱을 열었을 때 오늘 화면이 새 5끼로 열리는지 (기본 플랜 이관).
   이 창에서는 v1.8 상태를 인공적으로 재현해 확인했지만, 실제 기기의 낡은 서비스 워커 +
   실제 데이터로 다시 봐야 한다.
2. **과거 날짜(기록 탭)** — 8월 4일 이전 기록이 예전과 같은 마크·단백질을 보이는지.
3. **`바꾸기 ▾` 탭 정확도** — 44px 최소 높이지만 폭이 좁다 (엄지로 눌러보고 판정).
4. **보충 블록 헤더 길이** — timeHint 안내가 실기기 폭에서 두 줄이 되는지, 그게 거슬리는지.
5. **알림 다시 내보내기** — 플랜 id가 바뀌었으므로 ics UID도 바뀐다 (`shake.cut-1800-u`).
   기존 캘린더 알림을 지우고 다시 넣어야 중복이 안 생긴다 (패널 문구가 이미 그 말을 한다).
6. **다리살 며칠 써 보기** — 5-b가 실제로 마찰을 없애는지 (매일 ▾를 안 누르게 되는지).
