## 2. 반복된 결함 패턴 — **두 가지다** (내가 앞서 "같은 부류 5건"으로 뭉갠 것)

정확히는 뿌리가 같은 **두 하위 패턴**이다. 공통 뿌리는 "그 값의 진실 원천이 둘 이상"이다.

### 패턴 A — 파생 가능한 값을 손으로 적어 고정했다 (원본이 바뀌면 낡는다)

| # | 어디 | 무엇이 어긋났나 | 어떻게 고쳤나 |
|---|---|---|---|
| A1 | README 번들 크기 표 | 347KB/112KB로 적어뒀는데 T8~T12로 코드가 늘어 실제 **384KB/122KB** | 실측해서 갱신 (여전히 손으로 적은 값 — 아래 "남은 위험" 참조) |
| A2 | README 백업 크기 | "세션당 4.3KB → 240세션/18개월". 세션 수가 적을 때 측정해 **고정 오버헤드(루틴+카탈로그 16.5KB)가 세션당으로 분배**된 값이었다 | 고정분과 세션당 증가분(3KB)을 분리해 다시 측정 |
| A3 | 식단 `kcalLabel` | 시드 JSON에 "약 1,796kcal"을 적었는데 항목 합계는 **1,781**. cut-1500 단백질도 문서 166g / 실제 **162g** | 라벨을 **항목 합계에서 파생**시키고 "라벨 == 파생값"을 테스트로 고정 |

### 패턴 B — 같은 값을 두 코드 경로가 각각 계산했다 (입력이 달라 답이 갈라진다)

| # | 어디 | 두 답 | 원인 |
|---|---|---|---|
| B1 | 증량 무게 (F6) | 세션 화면 칩 "40 → **45**kg" / 실제 세트 **42.5**kg | `SessionScreen`은 `scales`를 넘기는데 `buildSession`은 안 넘겼다 |
| B2 | 식단 훈련일 여부 | 화면 **6슬롯** 판정 / 캘린더·월요약·내보내기 **5슬롯** 판정 | 화면은 `trained \|\| stored` 파생, 나머지는 `stored` 그대로 |

**A와 B의 차이:** A는 "값을 저장해서 낡음", B는 "계산을 두 곳에서 해서 갈라짐".
처방도 다르다 — A는 저장을 없애고 파생 함수로, B는 계산을 한 곳(chokepoint)으로 모은다.

### 이 프로젝트가 이미 쓰고 있는 처방 (chokepoint)

같은 뿌리를 앞선 라운드에도 세 번 만났고, 그때마다 함수 하나로 모았다:

| chokepoint | 무엇을 모았나 | 없으면 생기는 증상 |
|---|---|---|
| `derive.doneSets()` | 워밍업 제외 (T7) | 볼륨·PR·Phase 조건 중 한 곳만 빠뜨려도 조용히 틀린 숫자 |
| `derive.routineExerciseOfEntry()` | 대체 수행 해석 (T8/F1) | 대체한 세트의 볼륨이 0으로 사라짐 |
| `weightScale.isInverseKey()` + `nextWeightForProgression()` | 어시스티드 방향 (F2) | 보조를 늘렸는데 "최고 무게 PR" |
| `weightScale.easierWeight()` | "더 쉽게"의 방향 (F2) | 보상작용 하향이 더 어렵게 만듦 |
| `diet.resolveTrainingDays()` (신규) | 훈련일 사실 우선 (B2) | 화면과 내보내기가 다른 슬롯 수로 판정 |

**리뷰 요청 1:** 이 목록이 완전한지. 특히 "entry/day를 다루면서 chokepoint를 우회하는 경로"가
더 있는지 독립적으로 확인해주면 좋겠다. F1에서 `findRoutineExercise`의 export를 제거해
길 자체를 막았지만, 식단 쪽에는 아직 그런 봉쇄가 없다.

### 테스트 작성에서 의식적으로 한 것

1. **수정의 근거를 함께 고정한다.** "술어를 빼면 거짓 PR이 실제로 뜬다", "병합하지 않으면
   한 세션 뒤처진다", "정규화하지 않으면 슬롯 수가 갈라진다" — 수정이 되돌려지면 즉시 실패한다.
2. **인바리언트 파일**(`substituteCoverage.test.ts`) — "새 파생 경로를 추가하면 여기에 한 줄
   추가"가 규칙. 같은 결함이 세 번 반복돼서 만들었다.
3. **기계적 강제**(`seedRevision.test.ts`) — 시드 JSON 내용 해시와 `seedRevision`을 쌍으로
   고정. 둘 중 하나만 바꾸면 실패하므로 "고쳤으면 올려라"가 관례가 아니라 규칙이 된다.
4. **개수를 단정하지 않는다.** `expect(EXERCISES).toHaveLength(17)`이 T8에서 깨졌다.
   지켜야 하는 성질은 "빠진 종목이 없다"이고 개수는 그 성질이 아니다.

**리뷰 요청 3:** 테스트가 실제로 지키고 있는지. 특히 `substituteCoverage`와
`seedRevision`이 의도한 방식으로 실패하는지 (일부러 깨뜨려 확인해주면 좋겠다).

## 6. 미해결 · 판단 필요

### 6.1 [중간] 패턴 A가 README에 아직 남아 있다

번들 크기 표(A1)와 백업 크기(A2)를 실측으로 갱신했지만, **여전히 손으로 적은 값**이다.
다음에 코드가 커지면 또 낡는다. 선택지:
① 그대로 두고 릴리스마다 갱신하는 관례 ② 빌드 산출물에서 생성하는 스크립트 +
CI에서 어긋나면 실패 ③ 문서에서 구체 수치를 빼고 "측정 방법"만 남긴다.
**내 권고: ③** — 이 수치는 독자에게 "무겁다/가볍다"만 전달하면 되고, 정확한 값은
`npm run build` 출력이 이미 말해준다.

### 6.2 [낮음] 식단 쪽에는 chokepoint 봉쇄가 없다

운동 쪽은 `findRoutineExercise` export를 제거해 우회로를 막았다. 식단은
`resolveTrainingDays`를 `useDiet`에서 한 번 걸지만, 누군가 `db.dietDays`를 직접 읽으면
정규화를 건너뛴다 (백업은 의도적으로 raw를 쓴다). lint 규칙이나 인바리언트 테스트로
막을 만한지 판단 요청.

### 6.3 [낮음] 식단 플랜 교체 시 과거 기록 해석

플랜 항목 id가 바뀌면 과거 `checkedItemIds`가 매칭되지 않아 점수가 낮게 나온다.
현재는 "플랜에 없는 id는 세지 않는다"로 처리하고 테스트로 고정했지만,
**과거 날짜의 점수가 조용히 바뀐다**는 뜻이다. 운동 쪽 "루틴에 없음" 뱃지처럼
표시로 알릴지 판단 요청.
