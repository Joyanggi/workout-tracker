## 2. 이 두 라운드의 성격 — **조사가 전제를 세 번 흔들었다**

이전 라운드들과 다른 점이다. 세 번 모두 "그럴듯한 가설"이 틀렸고, 조사가 그것을 밝혔다.

| # | 그럴듯했던 가설 | 조사 결과 |
|---|---|---|
| W2 | 틱과 템포 가이드가 설정 플래그를 잘못 공유한다 (계획서의 가설 A) | **재생 로직은 정상.** 모든 restSec에서 3·2·1이 정확히 발화. 원인은 음향이었다 |
| W1/X5 | 숫자 입력은 `inputMode` 때문에 원래 제안이 안 붙는다 (**내 결론**) | **반례 하나로 무너졌다** — 마이마운틴 분 입력이 `inputMode="numeric"`인데 제안이 뜬다 |
| X3 | 훈련일 판정이 한 곳에 있다 (계획서 지목) | **네 곳**이 각각 계산하고 있었다 |

**W2가 특히 그렇다.** 사용자 보고에 "템포 가이드를 켜면 틱도 나는 것 같다"는 관찰이 있었고,
그게 플래그 공유 가설을 만들었다. 코드에서 A·B·C 세 가설을 다 죽인 뒤, 훅의 판정을
순수 함수(`createCountdownTicker`)로 꺼내 **실제 코드로** 재현했다 — restSec 45~180초 전부에서
3·2·1이 한 번씩 발화한다. 코드는 옳게 울리고 있었고, **울리는데 안 들렸다.**

실효 음량을 계산했다:

| 요인 | 틱 (330Hz·80ms) | 차임 (880/1320Hz) |
|---|---|---|
| 폰 스피커 저역 롤오프 (공진 아래 12dB/oct) | **−13.3 dB** | −1.5 / −0.3 dB |
| A-가중 (청감) | **−6.3 dB** | −0.4 / +0.7 dB |
| 시간 적분 (귀의 창 ~200ms) | **−4.0 dB** | −0.5 / 0 dB |

**차임이 틱보다 약 31 dB 크다.** 31 dB 중 **23 dB가 주파수와 길이**에서 온다.
그래서 **계획서의 처방(게인만 올리기)을 따르지 않았다** — 틱 +1.9dB / 차임 +3.5dB로
격차가 **32.9 dB로 벌어져 증상이 악화된다.** 사용자가 보고한 것은 절대 음량이 아니라 격차였다.

구분 근거를 **높이에서 형태로** 옮겼다: 틱 784Hz 단음 하나 / 마지막 큐 1319Hz 두 번 /
차임 880→1175→1568 세 음. 셋 다 스피커가 잘 내는 대역이고 **음 개수만으로도 구분된다.**
결과: 틱 **+20.5 dB**, 차임 +3.2 dB, 남은 격차 14 dB.

**"관찰은 정확했고 인과 추론만 나와 함께 틀렸다."** 사용자가 실제로 들은 것은 가이드
카운트인의 **같은 330Hz 틱**이었고, 가이드는 폰을 가까이 든 조용한 상태에서 쓴다.
같은 소리를 다른 조건에서 들은 것이지 코드 차이가 아니었다.

## 3. X3 — 이 라운드의 핵심 (보고 2건, 뿌리 하나)

보고 ① "D1 날 유산소만 했는데 다음날 D4 추천" ② "휴식일 골랐는데 훈련일로 강제 고정".
화면도 기능도 다르지만 원인은 한 줄 — **두 코드 모두 "완료 세션"을 "근력 수행"으로 취급했다.**

세트를 하나도 체크하지 않은 세션도 `endedAt`이 있으면 완료 세션이다. 그것이
회복 감쇠(×0.3)와 식단 훈련일 강제를 발동시켰다. 계획서가 점수를 재계산해 확인해 뒀다:
원점수 **D1 26.1 > D4 23.85 > D2 22.2**인데 D1이 페널티로 7.8이 되면서 D4가 이긴다.
**사용자 직관("볼륨이 안 채워졌으면 D1 유지")이 정확히 맞았다.**

chokepoint 3개 신설 (`derive.ts`):

```ts
hasStrengthWork(session)    // 작업 세트 1개 이상 (doneSets — 워밍업 제외)
strengthSessions(sessions)  // 완료 + 근력, 최신순
strengthDates(sessions)     // 날짜 집합
```

**적용한 곳**: `suggestNextDay`(감쇠·복귀 gap·하체 가드) · `daysSinceDay` ·
`weekCounts`(디로드·Phase 0) · `useDiet`(훈련일 정규화) · `DietScreen` · `HistoryScreen` ·
`SessionDetailScreen`(X1).

**적용하지 않은 곳이 더 중요하다**: 주간 도트·streak·기록 목록·내보내기는 그대로 뒀다.
헬스장에 간 것은 사실이고, 그 사실을 지우면 다른 종류의 거짓말이 된다. 대신 두 기준이
**갈릴 때만** 홈에 한 줄이 뜬다 — "유산소만 한 날도 불꽃으로 표시합니다 — 디로드·Phase
카운터는 근력 N회로 셉니다." 항상 적으면 잡음이고, 안 적으면 다른 숫자가 버그로 보인다.

### 3.1 계획서가 네 곳 중 한 곳만 지목했다

"그날 훈련했나"를 묻는 코드를 전수 조사하니 **네 곳**이 각각
`completedSessions(...).some(s => s.date === X)`를 계산하고 있었다 —
식단 정규화 · 오늘 식단 · 과거 식단 편집 · 홈 칩. 계획서는 첫 번째만 지목했다.

그리고 홈에서 **B2 결함의 사본**을 발견했다. `trained || (stored?.isTrainingDay ?? false)` —
식단 라운드에서 "정규화를 `useDiet` 한 곳으로 모았다"고 선언한 그 정규화의 사본이
살아남아 있었다. 고치지 않고 **계산 자체를 삭제**했다.

**"한 곳으로 모았다"는 선언은 사본을 다 지웠다는 뜻이 아니었다.** 새 chokepoint를 만들 때
"기존 계산을 지웠는지"를 따로 확인해야 한다 — 모으는 것과 지우는 것은 다른 작업이다.

## 4. 계획서와 다르게 판단한 것 (6건)

| # | 항목 | 무엇을 다르게 했나 |
|---|---|---|
| 4.1 | **W2** | 게인만 올리는 처방을 거부. 그 처방은 격차를 31→32.9dB로 **벌린다** (§2) |
| 4.2 | **W4** | 자동 닫힘을 **화면이 보일 때만 예약**한다. 잠긴 사이 끝났으면 복귀 순간 바가 즉시 사라져 "휴식이 끝났다"를 못 본다 — 확인 버튼을 없애려다 정보를 없애는 셈 |
| 4.3 | **X1** | "여러 세션인 날은 마지막 상세 하단에만" 규칙을 두지 않았다. 한 번에 한 상세만 보이므로 중복이 없고, 한쪽에만 나오면 "왜 여기선 안 보이나"가 된다 |
| 4.4 | **X1** | 요약을 새로 만들지 않고 `DietDayEditor`를 그대로 붙였다 (D3 원칙). 요약을 따로 만들면 식단 상태를 그리는 코드가 **세 벌**이 된다 |
| 4.5 | **X2** | `Adherence`에 값을 더하지 않고 `partialDates` 집합을 냈다. 판정 기준 3슬롯 유지가 요구였고, `good/mid/poor`의 의미가 바뀌면 과거 날의 마크가 전부 흔들린다 |
| 4.6 | **X5** | 해제를 focus 이벤트에만 의존하지 않게 바꿨다 (§5.2). **이후 트릭 자체를 지웠으므로 이 항목은 기록으로만 남는다** — 교훈(§5.2)은 유효하다 |

### 계획서보다 **넓게** 한 것 2건

- **X3**: 적용 지점이 4개가 아니라 7개였다 (§3.1)
- **X10**: 패널이 쓰던 `beep.ts` 진단 API 67줄이 죽은 코드로 남았다. X10 자신의 논리
  ("살려두면 유지 대상만 는다")를 그대로 적용해 제거. `audioSessionSupported`도 지웠다 —
  테스트만 쓰고 있었고, 그 술어는 `configureAudioSession`의 판정을 **복제한 두 번째 사본**이었다.
  테스트는 술어 대신 **효과**(type이 ambient가 되는가)를 단정하도록 고쳤다.
  **프로덕션 코드가 테스트만을 위해 존재하면 그건 테스트가 잘못 물어본 것이다.**

### 5.1 rAF가 조용히 죽는다

W2 검증 중 하네스의 `requestAnimationFrame` 루프가 30초 툴 제한에 걸려 죽었다 —
**배경 탭에서 rAF는 아예 호출되지 않는다.** 그 사실이 X5 구현을 바꿨다: readOnly 해제 후의
재포커스를 rAF로 걸어 뒀다가 `setTimeout`으로 바꿨다. rAF는 화면이 안 보이면 재포커스가
**영구히 유실**되고, 타이머는 지연될 뿐 실행은 보장된다.

### 5.2 실패의 방향을 고른 일 (X5) — **트릭은 이후 삭제됐다 (§7.1)**

readOnly 트릭을 `onFocus`에서만 해제하도록 구현하고 브라우저에서 확인했더니
**필드가 영구히 readOnly로 남았다.** 창에 OS 포커스가 없으면 `activeElement`는 설정되지만
focus 이벤트가 배달되지 않는다. 환경 특이사항으로 넘길 수도 있었지만, 그 상태의 사용자는
**아무것도 입력할 수 없다** — 연락처 제안이 뜨는 것보다 훨씬 나쁘다.

마운트 직후 타이머로 **무조건 해제**하고 `onFocus`는 보조 경로로만 남겼었다.
(그리고 결국 트릭 전체를 지웠다 — 방어할 수 있는 실패 모드였지만, **방어가 필요한 코드를
기대 이익 0에 얹는 것 자체**가 §7.1의 논점이었다.)
**실험이 실패하는 방향은 "제안이 계속 뜬다"(현상 유지)여야 하고, "입력이 안 된다"는
허용되지 않는다.** 실패는 피할 수 없지만 실패의 방향은 고를 수 있다.

## 7. 내가 스스로 의심하는 것 (리뷰 핵심)

### 7.1 [높음→해소] X5의 readOnly 트릭 — **지웠다** (사용자 결정, 2026-08-06)

> **✅ 권고 ②가 채택됐다.** 트릭을 제거하고 실기기 확인 4번을 목록에서 뺐다.
> 되살리기를 막기 위해 "readOnly 트릭이 남아 있지 않다"를 테스트로 두었다 —
> 지우려면 아래 이유를 다시 읽게 된다. 테스트 595 → **590** (트릭 관련 5개 → 부재 확인 1개).
> 비표준 토큰(`autocomplete="nope"`)은 남겼다: 실험대에서 이것도 무효로 나왔으니 지워도
> 되지만 이번 수정의 범위가 아니었다 (한 단어면 빠진다).
>
> 아래는 판단 근거의 기록이다.

해제가 **한 macrotask 뒤**에 일어나므로 readOnly 창이 사실상 0에 가깝다.
고전 트릭은 "탭하는 순간 필드가 읽기 전용"이어야 작동하는데, 우리 흐름에서는 필드가
✎ 탭으로 **마운트되면서** readOnly로 생기고 곧바로 해제된다. iOS가 그 사이 제안 부착을
건너뛸지는 반반이고, 내 판단으로는 **안 될 확률이 더 높다.**

그 대가로 남는 것: 상태 하나 + 이펙트 하나 + 포커스 핸들러 하나가, **운동 중 실제로
타이핑하는 유일한 텍스트 필드**에 붙어 있다. 그리고 그 경로에는 §5.2의 치명적 실패 모드가
있었다 (방어했지만 존재했다).

계획서가 "최후 시도"로 승인한 것이고 되돌리기는 두 줄이지만, **기대 이익이 거의 0인
복잡도를 그 필드에 얹는 것이 맞나**는 별개 판단이다.

**판단 요청:** ① 실기기 결과를 보고 결정 (현행) ② 지금 지우고 "플랫폼 제약"으로 종결
③ readOnly 창을 의도적으로 늘려(예: 250ms — 키보드 애니메이션과 겹치는 구간) 트릭에 실제
기회를 준다. **내 권고는 ②** — 실기기 확인 항목을 하나 줄이는 값이 이 트릭의 기대값보다 크다.
다만 사용자가 이미 실험에 동의했으므로 ①도 합리적이다.

### 7.2 [높음] v1.3 #4("모든 소리가 안 들린다")의 **근본 원인이 기록되지 않았다**

경과는 이렇다: 사용자가 모든 소리가 안 들린다고 보고 → 내가 소리 진단 화면을 만들어 배포
(즉시/지연 재생 · ambient vs playback · 신호 4종 · 상태 로그) → 사용자가 이후 "정상"이라고
확인 → X10에서 진단 화면 삭제.

**그런데 원인이 무엇이었는지가 어디에도 적혀 있지 않다.** PLAN-v1.4 X10에 "원인 규명 종료 +
사용자 '정상' 확인"이라고만 있다. 무음 스위치였는지, 볼륨이었는지, 출력 경로였는지,
아니면 W2의 음향 수정이 실제로 해결한 것인지 나는 모른다. 그리고 **계측기를 지웠다.**

재발하면 처음부터 다시 만들어야 한다. 이 프로젝트가 "측정해서 찾은 결함"을 자산으로
관리해 온 것에 비하면 예외적인 공백이다.

**판단 요청:** ① 사용자에게 당시 무엇을 보고 정상 판정했는지 물어 기록에 남긴다
② 진단 화면을 되살린다 (X10 반대) ③ 공백을 인정하고 재발 시 git 이력에서 복원한다.
**내 권고는 ①** — 계측기는 이력에 있으니 복원은 싸고, 없는 것은 **그때의 관측**이다.

### 7.3 [중간] X2가 `unlogged`를 둘로 쪼갰는데 **캘린더만 안다**

"기록 있음 / 판정 전"은 `DietMonthStats.partialDates`에만 있다. 내보내기·홈 칩·월 요약은
여전히 구분하지 않는다 — 캘린더는 회색 링을 그리는데 내보내기에는 그 날이 아예 없다.

의도적이었다 (`Adherence`를 건드리지 않는 것이 요구였다). 하지만 **같은 사실을 어떤 화면은
알고 어떤 화면은 모르는 상태**이고, 이 프로젝트가 반복해서 고친 형태가 그것이다.

**판단 요청:** 지금 상태로 두는 것이 맞는지, 아니면 `partialDates`를 내보내기·칩까지
전파해야 하는지. **내 권고는 현행 유지** — 캘린더는 "한 달을 훑는" 용도라 "손댄 날"
표시가 값이 있고, 내보내기는 LLM 분석용이라 판정 불가한 날을 넣으면 잡음이다.
다만 **그 비대칭을 문서에 명시**해야 한다.

### 7.4 [중간] X7이 백업 빈도를 크게 올렸는데 상한이 없다

이제 식단 변경마다 8초 debounce 후 업로드된다. 하루 종일 조금씩 고치면 업로드가 수십 번
일어날 수 있고, 매 업로드가 **전체 백업(약 47KB)** 이다. GitHub gist API 한도는 넉넉하지만
상한도, 일일 캡도, "내용이 안 바뀌면 건너뛰기"도 없다.

**판단 요청:** debounce만으로 충분한지, 아니면 ① 최소 업로드 간격(예: 5분) ②
직전 업로드와 내용이 같으면 건너뛰기 중 하나가 필요한지. **내 권고는 ②** —
해시 비교 한 줄이고, 근본 낭비(같은 내용 재업로드)를 없앤다.

### 7.5 [중간] X3의 기준(작업 세트)이 워밍업만 한 날을 "훈련 안 함"으로 본다

`hasStrengthWork`는 `doneSets`(워밍업 제외) 기준이다. 그래서 워밍업만 여러 세트 한 날은
회복 감쇠도 없고 식단 훈련일도 아니다. 의도한 선택이고 테스트로 고정했지만
("랙에 올려만 보고 그만둔 날은 감쇠할 회복이 없다"), **경계 사례에서 사용자 감각과
어긋날 수 있다** — 워밍업을 5세트 했으면 몸은 훈련한 것에 가깝다.

**판단 요청:** 현행 유지 / 워밍업도 근력으로 볼지. **내 권고는 현행 유지** — 워밍업 세트는
볼륨·PR·Phase 판정에서 이미 전부 제외되므로 기준을 하나로 두는 것이 일관된다.

### 7.6 [낮음] 커밋 메시지의 테스트 개수를 세 번 틀렸다 (관행 문제)

415 vs 410 · 529 vs 536 · 596 vs 595. 매번 **실행 출력이 아니라 기억으로** 적어서 생겼다.
한 번은 푸시 전이라 amend했고, 두 번은 푸시 후여서 다음 문서에서 정정했다.

기계적 방어가 가능하다: 커밋 메시지에 개수를 적지 않고 "테스트 통과"만 쓰거나,
`npm test` 출력을 붙여넣는 것을 관행으로 한다.

**판단 요청:** 개수를 아예 적지 않는 것이 맞는지. **내 권고는 "적되 출력에서 복사"** —
개수 변화는 리뷰에 유용한 신호다. 문제는 개수가 아니라 기억으로 쓴 것이다.

   전부 통과하지만, 3번은 **테스트를 지우는 쪽**이라 성격이 다르다.
