# PLAN v1.10 — 저녁 다리살 + 단백질원 짝 연동 (EE1~EE2) + 복귀 배너 라벨 (EE3)

> 작성: Fable (리뷰어), 2026-08-06. 구현: Opus.
> 피드백: "점심 다리살 → 저녁 안심, 점심 안심 → 저녁 다리살이 자동으로. 저녁에 입이
> 터지니까 맛있는 다리살을 저녁에 배치할 확률이 높다."
>
> **원본**: 루틴 문서 15장 로테이션 표 2026-08-06 개정 — 저녁 다리살 변형 신설
> (320g · 그날 점심 오일 + 오후 아몬드 생략 = 실효 +14kcal) + **"다리살은 하루 한 끼만"**
> 규칙. 요구의 전제(저녁 다리살)가 문서에 없었으므로 예산 재배치로 먼저 성립시켰다 —
> 저녁 만족도 = 폭식 방지 = 이행률이라는 근거가 문서의 중단 조건과 직결된다.

## EE1. 저녁 다리살 변형 (문서 미러링)

**설계**:

1. `cut-1800-u`·`cut-1500-u` 저녁 닭가슴살 품목에 변형 추가:
   `닭다리살 320g · 그날 점심 오일·오후 아몬드 생략` (kcal 544 · proteinG 51).
   점심 다리살(v1.9)과 같은 방식 — 조건은 문구로, 강제는 하지 않고, kcal 합계가
   사실을 보여준다 (조건을 어기면 +274가 그대로 보인다).
2. 플랜 데이터만 바뀌므로 **플랜 id는 유지한다** — 변형 추가는 기존 기록의 판정을
   바꾸지 않는다 (variantChoices 부재 = 기본 변형 = 가슴살, v1.9 §5.2의 완결성 그대로).
   ⚠ 단 이것이 성립하는지 이름 붙은 테스트로 확인할 것: "변형 추가 전 기록된 저녁
   슬롯의 마크로가 변하지 않는다."
3. 문서 로테이션 표와 1:1 대조 테스트 갱신 (저녁 3택: 가슴살/안심/다리살).

## EE2. 단백질원 짝 연동 — 표시 기본값 수준

**설계 원칙**: 자동 연동은 **기록이 아니라 표시 기본값**에만 작용한다. 앱은 사용자
대신 기록하지 않는다 — 그날 점심에 무엇을 골랐는지에 따라 **아직 기록되지 않은 저녁의
초기 표시**가 짝으로 바뀔 뿐이고, 기록되는 순간 `seedVariantChoices`(v1.9 §5.2)가
화면의 선택을 기록에 새기는 것은 그대로다.

1. 순수 함수 `pairedVariant(slotId, itemId, todayChoices, defaults)` — 우선순위:
   **① 그 슬롯의 기록된 선택 > ② 같은 날 짝 슬롯의 기록에서 파생된 짝 > ③ 기억된
   기본값(variantDefaults) > ④ 기본(0)**.
2. 짝 규칙 (문서 "하루 한 끼만"의 표현):
   - 점심 = 다리살 → 저녁 초기값 = **안심**
   - 점심 = 안심 → 저녁 초기값 = **다리살**
   - 점심 = 가슴살 → 저녁은 ③(기억된 기본값) 그대로
   - 역방향 동일 (저녁을 먼저 기록한 날: 저녁 다리살 → 점심 초기값 안심)
3. 짝 파생이 ③(기억)보다 우선하는 이유: 기억은 "평소의 나"이고 짝은 "오늘의 사실"이다 —
   오늘 점심에 이미 다리살을 먹었다는 사실이 평소 기본값보다 강하다.
4. 저녁 다리살이 초기값이 되는 날, 오후 아몬드·점심 오일 슬롯은 **건드리지 않는다**
   (강제 금지 — v1.9 DD3.5와 같은 원칙). 조건은 변형 문구가 말하고 합계가 검증한다.

**검증**: `pairedVariant` 우선순위 4단 테스트 · 짝 규칙 3경우 + 역방향 · "짝 파생은
기록을 만들지 않는다" (v1.9 §5.3의 유령 기록 금지 그대로) · 점심 다리살+저녁 다리살을
**막지는 않되** 그 조합에서 합계가 +174를 정직하게 보여주는 시나리오 고정.

## EE3. 복귀 배너의 한 칸 토글 — 상태인지 동작인지 읽히지 않는다

> 2026-08-24 사용자 피드백으로 이 라운드에 합류. 식단(EE1·EE2)과 축이 다르다.
>
> 피드백: "맨 위에 19일 공백 ~~~ 하고 적용됨/무시 버튼이 있는데, 누르면 적용이 됐다는
> 건지 무시가 됐다는 건지 모르겠어."

**진단은 라벨의 문법이다.** 같은 자리의 글자가 한 번은 상태("적용됨")를, 한 번은
동작("무시")을 말했다. 문법이 번갈아 바뀌면 지금 상태를 읽은 것인지 누르면 벌어질 일을
읽은 것인지 구분할 방법이 없다 — 켜짐/꺼짐이 **글자 하나로만 구별되는 한 칸 토글**의
전형적인 실패다. 배너가 던진 것은 "복귀할까요?"라는 질문인데 답이 하나만 보였다.

**두 번째 원인: 눌러도 화면이 그대로다.** 토글은 다음 세션 생성만 바꾸는데
(`HomeScreen.create`의 `isReturn`), 카드는 끈 뒤에도 "N일 공백 — Day 1로 가볍게
복귀합니다"라고 말했다. 눌린 결과가 어디에도 나타나지 않으니 라벨을 의심하게 된다.

**설계**:

1. 배너의 답을 **두 칸으로 나란히** 놓는다 (`.banner-choice`, `role="group"`).
   `[적용] [안 함]` — 고른 쪽만 채우고(`aria-pressed`) 나머지는 테두리만 둔다.
   기존 `.segment`와 같은 표현이고, 선택은 글자가 아니라 **비교**로 읽힌다.
   토글 뒤집기(`setApplyReturn(!applyReturn)`)를 없애고 각 버튼이 값을 그대로 넣는다.
2. 순수 함수 `returnChoiceReason` — "안 함"이면 카드 문구가
   `N일 공백 — 복귀 프로토콜 없이 평소 강도로 시작합니다`가 된다. 배너는 묻고 카드는
   그 답의 결과를 말한다. 복귀 제안이 없을 때·공백 일수를 모를 때(`gapDays: null`)는
   제안 근거를 그대로 쓴다.
3. 상태는 그대로 컴포넌트 상태다 — 저장하지 않는다 (AA1의 `pickedDayId`와 같은 결).

**검증**: `returnChoiceReason` 4경우(적용/안 함/제안 없음/gapDays null) · 소스 스캔으로
한 칸 토글 복원 금지(`'적용됨'` 부재, 삼항 라벨 부재, `setApplyReturn(!applyReturn)`
부재) · 배너 두 버튼의 `aria-pressed` 배선 · 카드 문구가 `returnChoiceReason`을 거치는지.

범위 제외: 배너를 dismiss 가능하게 만드는 것(복귀는 다른 배너와 달리 **다음 세션의
내용**을 정하므로 "나중에"가 아니라 답이 필요하다) · 선택의 저장.

## 구현 순서와 검증

EE1 → EE2. EE3은 식단과 무관하므로 순서에 매이지 않는다. 관례 그대로: `npm run build` · 커밋 개수 실행 출력 복사 · heredoc `<<'MSG'` ·
새 스캔 결함 복원 확인 · 과거 판정 불변 확인 절 · 완료 후 DEV-RECORD-v1.10 ·
package.json 1.10.0.

범위 제외 (재론 방지):
- 짝 조합의 강제 (하루 두 끼 다리살 차단 등) — 앱은 판단하지 않는다, 합계가 보여준다
- 아몬드·오일 슬롯 자동 조정 — 같은 이유
- 주간 로테이션 스케줄러 (요일별 자동 배정) — 요구된 적 없음
