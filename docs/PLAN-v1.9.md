# PLAN v1.9 — 식단 단순화 라운드 (DD1~DD4)

> 작성: Fable (리뷰어), 2026-08-06. 구현: Opus.
> 원 피드백 4건 전부 채택. **루틴 문서 15장이 먼저 개정됐다** (2026-08-06 — 끼니 배치
> 통일 + 단백질원 로테이션 표 신설). DD2~DD4는 그 문서를 미러링한다.
>
> **이 라운드의 인바리언트: 과거 날짜의 판정이 하나도 바뀌지 않는다.**
> 플랜 변경은 전부 **새 플랜 id**로 하고, 과거 DietDay는 자기 planId로 계속 판정된다
> (DietDay가 planId를 저장하는 구조가 이 라운드를 위해 존재했던 셈이다).

## DD1. 두 플랜의 차이를 화면이 말하지 않는다

**피드백**: "보정 1,500과 감량 1,800 차이를 앱에서 잘 모르겠다."

**확인된 사실**: 차이는 **저녁 현미밥 1개(215kcal)** 하나다 (diet-plans.json 대조 —
1,781/166g vs 1,566/162g). 플랜 시트는 이름·총량만 보여주므로 사용자가 구분할 방법이
화면에 없다 — 몰랐던 게 당연하다.

**설계**:

1. 순수 함수 `comparePlans(base, other)` — 슬롯별 품목 diff를 파생한다
   ("저녁: 현미밥 1개 빠짐 · −215kcal"). 손으로 설명 문자열을 적지 않는다 —
   플랜 JSON이 바뀌면 설명도 따라와야 한다 (파생 원칙).
2. DietPlanSheet의 비기본 플랜 행 아래에 diff 한 줄 + 용도 문구("회식 다음 날 보정용 —
   연속 3일 상한"은 기존 경고 배너가 이미 담당하므로 중복하지 않는다).

**검증**: comparePlans 단위 테스트 (품목 추가·제거·수량 변경 케이스) + 현재 두 플랜의
diff가 정확히 "저녁 현미밥 1개"라는 이름 붙은 테스트.

## DD2. 훈련일/휴식일 통일 — 매일 같은 5끼

**피드백**: "총량이 같으니 휴식일로 통일하는 게 좋을 것 같은데 어때?"

**리뷰어 판정: 채택.** 근거는 문서 15장 개정 블록에 있다 — 총량·단백질 완전 동일,
차이는 쉐이크 배치뿐, 실사용 실수 사건에서 생리학적 무의미가 확인됐고, 훈련일 토글은
반복 혼란원(G3·X4 계열)이었다. "매일 같은 숫자"의 이행률 원칙을 구성까지 확장한다.

**설계**:

1. **새 플랜 id로 교체**: `cut-1800-u`·`cut-1500-u` (u=unified). `slots` =
   기존 `restDaySlots`(5끼) 하나로 통일 — 모델의 `restDaySlots` 분기 자체를 제거한다
   (타입에서 필드 삭제, `slotsFor` 단순화. 과거 플랜 데이터가 백업에 남아 있으므로
   읽기 하위호환은 유지 — 없으면 slots를 쓴다).
2. **과거 판정 불변**: 기존 `cut-1800`·`cut-1500`은 DB에 남는다 (과거 DietDay가
   자기 planId로 판정). 플랜 시트에는 새 플랜만 노출하고 옛 플랜은 숨긴다 (legacy 플래그
   또는 isDefault 아닌 것 중 대체된 id 목록). `defaultPlanId`는 새 플랜으로.
3. **UI 정리**: 훈련일/휴식일 세그먼트·"운동 기록이 있어 고정" 잠금·`resolveTrainingDays`
   정규화 — 전부 존재 이유가 사라진다. 제거하되, `resolveTrainingDays`는 과거 플랜 판정
   경로에 여전히 필요하므로 **과거 planId일 때만** 동작 (읽기 경계에 조건 한 줄).
4. **크리티컬 스킵**: `pre`/`post`는 새 플랜에 없으므로 `shake`만 남는다
   (CRITICAL_SKIP_SLOTS는 id 기반이라 자동 — 확인 테스트만).
5. 보충 블록 timeHint에 안내 승계: "15:00~16:00 · 훈련하는 날은 훈련 2시간 전까지".
6. 홈 식단 칩·알림 ics·내보내기는 슬롯 파생이므로 자동 반영 (확인만).

**검증**: 새 플랜이 문서 15장 개정 표와 1:1 (이름 붙은 대조 테스트) · 과거 날짜 판정
불변 (옛 planId 시나리오 고정) · 세그먼트 소스 부재 스캔.

## DD3. 단백질원 선택형 — 가슴살 / 안심 / 다리살

**피드백**: "식단 선택을 단백질 주요 구성원 선택으로. 가슴살은 팩, 안심·다리살은 g 표기."

**원본**: 문서 15장 "단백질원 로테이션" 표 (2026-08-06 신설) — 점심 3택, 저녁 2택
(다리살은 저녁에 쓰지 않는다 — 뺄 지방원이 없어 지방 예산 초과).

**설계**:

1. `DietItem`에 `variants?: { name; qty; kcal; proteinG }[]` — 첫 변형이 기본(가슴살).
   `SlotRecord`에 `variantChoices?: Record<itemId, number>` (additive — 백업 하위호환,
   부재 = 기본 변형).
2. UI: 변형이 있는 품목은 체크 시 그대로 기본으로 체크되고, **품목을 길게 안 누르게** —
   품목 옆 작은 "▾"로 변형 시트(가슴살 2팩 / 안심 180g / 다리살 200g + 오일 생략 안내).
   정상일 마찰(슬롯당 1탭)은 그대로여야 한다 — 변형 선택은 예외 경로.
3. **마크로 정직성**: `summarizeDietDay`가 선택된 변형의 kcal/proteinG를 쓴다
   (다리살 선택일의 kcal이 실제로 +45 나와야 한다 — 낙관적으로 뭉개지 않는다).
4. **점수는 변형 간 동등** — 문서가 셋 다 허용하므로 어느 것을 골라도 감점 없음.
   가중치(itemWeight)는 기본 변형 기준으로 고정 (선택에 따라 과거 점수가 흔들리지 않게).
5. 다리살의 "올리브오일 생략" 규칙은 **강제하지 않는다** (앱은 판단하지 않는다) —
   변형 qty 문구와 시트 안내로만. 어긴 날은 kcal 합계가 정직하게 초과를 보여준다.
5-b. **마지막 선택을 기억한다** — 슬롯×품목별 마지막 변형 선택이 다음 날의 기본이 된다
   (settings에 `variantDefaults: Record<slotId.itemId, number>` 저장). 사용자는 하나에
   꽂히면 오래 먹는 패턴이라(다리살 한 달 질문이 그 증거), 매일 ▾ 2탭은 불필요한
   마찰이다 — 한 번 "점심 다리살·저녁 안심"으로 고르면 이후는 슬롯당 1탭 그대로.
   **과거 날짜에는 소급하지 않는다** (기록된 variantChoices가 항상 우선, 기본값은
   미기록 날의 초기 표시에만).
6. 내보내기: 선택 변형을 그대로 표기 ("단백질원: 닭다리살 200g") — LLM이 로테이션
   패턴을 볼 수 있게.

**검증**: 변형 선택 → summarize 마크로 반영 · 부재 시 기본 · 백업 왕복 ·
문서 로테이션 표와 변형 정의 1:1 대조 테스트.

## DD4. 그램 표기 통일

**피드백**: "안심·다리살은 몇 g인지, 채소 1접시도 g으로."

**설계**: 문서 표 그대로 —
- 점심 변형: 가슴살 2팩 / **안심 180g** / **다리살 200g (그날 올리브오일 생략)**
- 저녁 변형: 가슴살 3팩 / **안심 270g**
- 채소: "1접시" → **"150g"** (kcal 0 취급 유지 — 표기만)

새 플랜(DD2)의 qty 문자열에 반영. DD2·DD3과 같은 시드/플랜 개정에 묶는다.

**검증**: DD3의 문서 대조 테스트에 포함.

## 구현 순서와 검증

권장: DD1 (독립·소형) → DD2 (플랜 교체 골격) → DD3+DD4 (새 플랜 위에 변형 모델).

- **소급 효과 — 없음이 목표이자 검증 대상이다.** 과거 DietDay는 옛 planId로 판정
  불변. DEV-RECORD에 "과거 판정 불변" 확인 절 필수 (이름 붙은 테스트 근거로).
- 플랜 교체는 diet-plans.json + 시드 경로 확인 (dietPlans 시드 갱신 관례).
- `npm run build` / 커밋 개수 실행 출력 복사 / heredoc `<<'MSG'` / 새 스캔 결함 복원
  확인 / 완료 후 `docs/DEV-RECORD-v1.9.md` / package.json 1.9.0.

범위 제외 (재론 방지):
- 칼로리 사이클링 (문서 909행이 이미 기각 — 이행률 우선)
- 다리살-오일 연동 강제 (앱은 판단하지 않는다 — kcal 합계가 사실을 보여준다)
- 단백질원 재고 관리·장보기 목록 (비목적)
