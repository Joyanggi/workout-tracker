## 1. 판정 — 1.1 inverseWeight (높음)

**결정: (c)+ 하이브리드. assisted-pullup은 유지한다.**

운동학 근거: 랫풀다운 자리가 없을 때 어시스티드 풀업은 움직임 패턴상 가장 가까운 대체이고, 이걸 빼면 그날 광배 수직당김이 통째로 빠진다. 기능 가치가 수정 비용을 넘는다. 단 (c) 원안(분석 전면 제외)만으로는 부족하다 — **프리필과 보상작용 하향은 "분석"이 아니라 실제 훈련을 조종하는 경로라서, 방향이 틀리면 기능 자체가 쓸 수 없다.**

경로별 처리 (전부 필수):

| 경로 | 처리 | 이유 |
|---|---|---|
| PR — 무게·e1RM | **inverse 종목 제외** | 방향이 반대라 거짓 PR. 제외가 정답 |
| PR — 반복수 (같은 무게) | **유지** | 같은 보조 무게에서 반복 증가는 inverse에서도 실제 진전이다. 이미 정확함 |
| `totalVolume` | inverse entry 제외 | 보조 무게 × 반복은 볼륨이 아님. 요약 화면에 "어시스트 종목 제외" 한 줄 |
| `strengthTrend` / 분석 차트 | inverse recordKey 제외 + 종목 히스토리 화면에 "보조 무게는 줄어드는 것이 진전" 안내 | v1.2에서 (b) 실효 부하 방식과 함께 재검토 |
| `prefill.better()` | **inverse면 비교 방향 반전** (작은 보조 = 더 나은 기록) | 안 고치면 2회차부터 가장 쉬웠던 세션이 기준이 됨 — 기능 성립 불가 |
| CompensationWatch stepDown | **inverse면 하향 = 보조 증가** | 현재는 "무게 하향"이 더 어렵게 만듦 — 적극적으로 해로움 |

구현 방식: 순수 함수에 카탈로그를 넘기지 말 것 (그 우려는 타당하다). 대신 **`isInverse: (recordKey) => boolean` 술어 하나를 파라미터로** 받게 하라. 호출부(화면·buildSession 호출처)는 전부 `bundle.catalog`를 이미 갖고 있다. 각 경로에 inverse 케이스 테스트 추가.

⚠ **순서 주의: 이 수정은 아래 2번(패턴 재발 수정)과 반드시 함께 커밋하라.** 현재 assisted-pullup이 차트에 안 나오는 것은 2번 버그가 우연히 가려준 것이다. 2번만 먼저 고치면 뒤집힌 차트가 노출된다.

## 2. 4장-2 답변 — 같은 패턴 재발: **있다. 3곳 + 죽은 코드 1곳**

세 곳 모두 entry 단위 순회라 `routineExerciseOfEntry(routine, entry)`로 바꾸면 끝난다 (drop-in).

추가: `dashboard.ts:360 isKnownRecord`는 **사용처가 0인 죽은 코드**다 (v1의 증량 배지 필터로 만들었다가 소비처가 사라진 듯). 삭제하라 — 남겨두면 다음에 누가 대체 recordKey에 이걸 써서 같은 버그를 만든다.

**재발 방지 (권장):** `findRoutineExercise`를 derive 내부 전용으로 낮추거나(export 제거가 안 되면 이름에 경고를 담아라), lint 규칙/테스트로 "entry를 다루는 파일에서 parseRecordKey + findRoutineExercise 조합"을 잡아라. 관례 주석은 이번에 두 번 뚫렸다.

## 3. 판정 — 1.2 구백업 복원 (중간)

**옵션 ② (복원 시 보정).** `parseBackup`에서 `fallbackDays[].recordDayId`가 없고 해당 fallback id가 번들 정의와 일치하면 번들 값으로 채운 뒤 검증한다. 마이그레이션 shim은 정확히 이런 곳(파싱 경계)에 두는 것이 맞고, 검증 완화(③)는 하지 마라 — 검증이 이번 P0을 잡은 장치다. 노출이 현재 0이라도 사용자가 과거에 파일로 내려둔 백업이 있을 가능성은 배제 못 한다.

## 4. 판정 — 1.3 루틴 version 규칙 (낮음)

**"시드 JSON 변경 시 seedRevision 필수 상향"을 테스트로 강제하라.** 관례로 두면 이번처럼 또 뚫린다:

- 시드 JSON에 `seedRevision: number` 추가, `ensureSeed`는 version 대신 이걸 비교
- **테스트**: 번들 루틴 JSON의 내용 해시를 스냅샷으로 두고, 해시가 바뀌었는데 seedRevision이 그대로면 실패 — "JSON을 고쳤으면 revision을 올려라"가 기계적으로 강제됨
- "매 부팅 재주입"은 기각 — 사용자가 같은 id로 수정 루틴을 가져온 경우를 덮어쓴다

## 5. 판정 — 1.4 전체 조회 (낮음)

**보류가 맞다.** 근거를 수치로: 1인용 주 3~4회 = 연 ~200세션, 세션당 ~2KB → 5년치 1,000세션 ≈ 2MB. iPhone IndexedDB toArray로 수십 ms 수준이고 홈 진입 시 1회다. **1,000세션(약 5년) 도달 전에는 인덱스 배관이 낭비다.** 나중에 체감되면 분석 탭의 `strengthTrend`부터 date 범위 쿼리로 좁혀라 (가장 긴 순회).

## 6. 4장-3 답변 — applySubstitute 거부 조건

**충분하다.** 체크된 세트 거부(워밍업 포함 — `s.done`이 워밍업도 잡음 ✓), 중복 recordKey 거부, 연쇄 대체 시 원 종목 보존(`substituteFor ?? recordKey` ✓), 감각·보상작용 미상속 ✓.

한 곳만 다듬어라: **원상복귀 경로에서 자기참조가 남는다.** 대체 후 (세트 체크 전에) 원 종목으로 되돌리면 `next.recordKey === entry.substituteFor`가 되는데, 이때 `substituteFor`를 지우지 않으면 "자기 자신의 대체"인 entry가 생긴다. `applySubstitute`에 `next.recordKey === (entry.substituteFor ?? entry.recordKey)`면 `substituteFor: undefined`로 클리어하는 한 줄 + 테스트.
